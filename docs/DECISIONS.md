# Decisions

A short running log of choices and the reasons for them, newest last. It includes design decisions where DESIGN.md is silent, and every dependency (license and reason, per CLAUDE.md 5).

## Project

- **License: Apache-2.0.** The user's choice, and the one CLAUDE.md recommends. It is permissive, has a patent grant and is accepted by F-Droid. Not GPL, which would bind the whole app.
- **Application ID: `io.github.ictashik.tapedash`.** The `io.github.<user>.<repo>` form is the usual one for an open-source app without its own domain. The GitHub handle is taken from the git identity's noreply address and has not been confirmed, and there is no remote yet. Renaming is a few lines until the first release and effectively impossible after it, so confirm it before then.
- **No remote.** The repository is local only. Nothing is pushed without the user's explicit say-so (CLAUDE.md 2).

## Toolchain

- **Flutter 3.44.1 stable, Dart 3.12.1.** Flutter stable only (CLAUDE.md 3). Android Gradle Plugin 9.0.1, Kotlin 2.3.20 and Gradle 9.1.0 come from that Flutter version's template. Needs JDK 17.
- **minSdk 24 and targetSdk 36 are Flutter's own defaults** (`flutter.minSdkVersion`, `flutter.targetSdkVersion`). Flutter's default minSdk is already Android 7.0, so there is nothing to override. We never raise it for convenience.
- **CI builds only `armeabi-v7a` and `arm64-v8a`**, the two ABIs we ship. A plain `--split-per-abi` release build also produces an x86_64 APK we do not want.

## Android

- **Launch window is `void`, in one theme only.** TapeDash is always dark (DESIGN.md 4.1), so there is no `values-night`. The launch drawable, `NormalTheme` and the Android 12+ splash background are all the `tapedash_void` colour, and `test/unit/platform/launch_theme_test.dart` fails if any of them drifts from `TapeColors.voidColor` or turns white. The default Flutter template used white and `?android:colorBackground`, which is what causes a white flash.
- **`android:allowBackup="false"`.** Android Auto Backup uploads app data to the user's Google account, and TapeDash is strictly offline. Trips leave the phone only through the CSV export.
- **Landscape comes from the manifest alone** (`sensorLandscape`, both directions). It works even with the phone's rotation lock on and avoids a portrait frame at launch, so there is no `SystemChrome` orientation call.
- **No permissions are declared yet.** Each one is added together with the feature that needs it, and must be on the allowed list in CLAUDE.md 4.
- **`uses-material-design: false`.** Material widgets and icons are banned (DESIGN.md 13.1), so the Material icon font is not bundled.

## Code

- **`TapeColors.voidColor`**, not `TapeColors.void`: `void` is a reserved word in Dart. Other tokens keep the DESIGN.md name with dots removed (`carbon900`, `etchStrong`) when they arrive in phase 3a.
- **`lib/main.dart` uses `WidgetsApp`**, not `MaterialApp`, so no Material code is linked in at all.

## Device features

- **`DeviceFeatures` is an interface**, with `DeviceChannel` (platform channels to `DeviceChannel.kt`) and `FakeDeviceFeatures` behind it. Code that needs the screen, battery or sensors takes the interface, so Daylight and Night switching and the phone-health logic can be tested headlessly.
- **One shared stream per sensor.** A Flutter `EventChannel` has one native handler, so a second `receiveBroadcastStream()` would silently take the sensor from the first listener. The streams are built once, and the sensor is only registered while something listens.
- **Brightness has a floor.** Dart clamps the level to 0..1 and rejects NaN, and the Android side never goes below 0.01, since some phones treat 0 as backlight off, which would blank the dash. The design floors (12% at night, 20% for the HUD) are policy for the brightness controller and are not enforced here.
- **Accelerometer axes are remapped in Dart.** Android reports the sensor in the phone's own axes, not the screen's. The Android side sends `[x, y, z, displayRotation]` untouched, and Dart turns it into screen axes (x right, y up the screen, z out of it), so the mapping is unit-tested and CI covers it. It matters because the app is landscape-only, so a phone held upright is still drawn rotated. Checked on emulators by rotating the emulated phone: with the display following the phone into either landscape, gravity reads +9.8 on screen y whichever rotation the OS reports.
- **Immersive mode** uses `WindowInsetsController` on Android 11+ and the legacy `systemUiVisibility` flags below, and is re-applied when the window regains focus. On Android 4.4 to 10 the OS shows a one-time "Viewing full screen" notice the first time an app goes immersive. It cannot be suppressed, and one tap on "Got it" dismisses it for good. Expect it on old phones.
- **Startup never waits on the window calls.** If hiding the bars or keeping the screen on fails, that is logged and the app starts anyway. Other errors, which would be bugs, are not swallowed.
- **Launch flash cannot be measured on emulators.** With the launch colour set to solid red, no red frame appears on either an Android 7.0 or an Android 16 emulator, so an emulator recording cannot show a white flash, broken or fixed. The launch resources are guarded by `launch_theme_test.dart` instead, and a check on a real phone is part of the hardware handoff.

  - The script has its own fixture tests (`test/unit/tool/check_offline_test.dart`), so a broken check cannot pass silently.

- **`.github/workflows/ci.yml`:** build the release APKs, then `tool/verify.sh --strict`, then `tool/check_apk_size.sh`. The build comes first because the strict offline check reads the merged release manifest it produces. It has not been run on GitHub yet, since there is no remote.

A moved tag or a new runner image cannot change what CI runs or the golden images it produces. Bump them on purpose. ## Simulator: the car (phase 1)

- **The physics is a Willans-line engine, not a lookup table.** Throttle sets manifold pressure through an orifice, air follows the speed-density formula of CLAUDE.md 8.4, fuel is air over the air-fuel ratio, and torque is the fuel's energy less pumping, friction and accessory losses. So MAF, MAP, load and fuel rate are consistent with each other by construction, which is what the fuel estimators have to be tested against. A petrol engine controls air first, and a diesel controls fuel first with a smoke limit. Fuel is cut on the overrun above 1,500 rpm while the air keeps flowing, so MAF stays non-zero with no fuel burnt, which is a trap for estimators.
- **Two powertrains.** A CVT, where engine speed follows the pedal more than road speed, and a manual, where a virtual driver changes gear with hysteresis and a dwell so the gearbox cannot hunt.
- **The physics does not depend on the seed.** Each part draws from its own forked stream, and the seed only changes the reported noise (idle wobble, sensor noise, GPS error). Two runs with different seeds burn exactly the same fuel, so a test can compare any two of them, and turning noise on can never move the ground truth.
- **Ground truth is exact and kept apart from what the ECU reports.** Cumulative fuel, distance, engine-on time, idle time and idle fuel (idle is under 2 km/h with the engine running, CLAUDE.md 8.7), and a log of every scripted hard-acceleration and hard-braking event. It is recomputed independently from the snapshots in the tests.
- **Deviations from the wording of CLAUDE.md 7.1, on purpose.**
  - Braking is 7.5 m/s2 plus drag and engine braking, about 8 m/s2 at most, and grip limits a launch to 0.36 g. The spec says "up to about 8".
  - Coolant reaches 85 C after 8 minutes of city driving and is then held at about 90 C by the thermostat, as specified, but idling warms an engine far more slowly, because a warm-up needs load: `cold_start_idle` is at 51 C after its 5 minutes. The spec's "8 to 10 minutes" holds for a drive, not for idling.
- **A scripted driver inverts the model.** It asks the vehicle model which pedal gives a wanted acceleration (`pedalForAcceleration`), so a speed is held smoothly and a stop is reached without overshoot. These what-if questions must never change the car, and must never trigger a gear change: an early version's what-if returned the clutch-out acceleration and made the driver slam the pedal to 1 and kick down for real. They are tested to change nothing.
- **Hard driving has to survive the app's own smoothing.** The coach smooths speed over about a second before it looks at acceleration (CLAUDE.md 8.8), which hides an acceleration that only just clears its threshold or does not last. A first version of the hard style passed a peak-over-threshold check and the app's detector found 6 of 12 scripted events. The hard style now asks for 3.6 and 5.0 m/s2 and the aggressive route runs at 64 km/h, and a test applies the app's rule to whole km/h samples at 10 Hz. The phase 5 requirement that detected counts match the scripted ones depends on this.
- **`eco_city` is 30% cheaper than `aggressive_city`** over the same 4.5 km (0.372 L against 0.535 L), with the same waits at the signals, so the saving is in the driving. The spec asks for at least 15%.
- **Profiles are approximations, not data from any real car** (CLAUDE.md 7.2). PID 01 is in none of the PID lists because every OBD-II ECU has it; the simulator always adds it.

## Simulator: the adapter (phase 1)

- **The byte format comes from the ELM327 datasheet, and the golden fixtures are written by hand from it.** The datasheet's own examples are the fixtures: `0100` giving `41 00 BE 1F B8 10`, the VIN as `014` and `0: 49 02 01 31 44 34`, and `01 04 05 0B 0C` as `00A` with the last line padded with zeros. All sixteen combinations of echo, linefeeds, spaces and headers are written out as literal strings, so the simulator is checked against the spec and not against itself.
- **The datasheet is written for a person at a terminal, so it leaves some byte-level conventions open.** These follow what real adapters are known to send, and **none of them has been checked against hardware**:
  - every reply ends with a blank line and then `>`, so `OK` is `OK\r\r>` (or `OK\r\n\r\n>` with linefeeds on);
  - after `ATZ` or `ATWS` the banner is preceded by two `\r`;
  - with spaces on, a data line ends with a space, as in `41 0C 1A F8 \r`;
  - a multi-frame line is `0:` and a space, then the bytes;
  - a lone carriage return repeats the last command;
  - `ATDP` names the CAN protocols as `ISO 15765-4 (CAN 11/500)`, with `AUTO, ` in front when it may search;
  - what the adapter prints for a fixed protocol the car does not speak: `BUS INIT: ...ERROR` for the K-line protocols, `NO DATA` for J1850 and 29-bit CAN, `CAN ERROR` for the other bit rates.
  The app's parser has to be tolerant of all of these anyway (CLAUDE.md 8.1), and the first real adapter session should be compared against them (see the hardware handoff notes in STATUS.md).
- **Behaviour was cross-checked against Ircama's ELM327-emulator by reading its source.** That project is CC BY-NC-SA 4.0, which is non-commercial and share-alike and so cannot be mixed into Apache-2.0 code. It was read for how real adapters are seen to behave, and nothing from it is in this repository, as code, text or data, and it is not a dependency. The optional cross-check in CLAUDE.md 7.5, running our parser against its output over TCP, is for phase 2 and needs the same care.
- **Adapter timing is an assumption, because the datasheet gives no figures:** a reset takes 0.8 s, finding a protocol 2.4 s (0.4 s if the stored one is right), an unreachable car 5 s to give up, the ECU answers in 20 ms, and adaptive timing waits 40 ms (AT1) or 25 ms (AT2) after the answer. Without adaptive timing, or on a clone that ignores it, the adapter waits its whole `ATST` timeout (200 ms) unless the request ends with a response-count digit. On the Bluetooth clone preset that makes a request without the digit about 300 ms and one with it about 100 ms, so three fast-tier PIDs asked one at a time without the digit are about 1 Hz. It is the reason the ELM layer should add the digit, or batch.
- **`AdapterQuirks.latency` is the link's round trip, and the adapter's own time comes on top of it.** The car is asked in the middle of the round trip, so a value is as old as half the latency by the time it arrives, and the app's timestamping at the midpoint of a request is exactly right. `Elm327Device` does this; `Elm327Simulator` itself has no notion of the link.
- **Only ISO 15765-4 CAN (11-bit, 500 kbaud, protocol 6) is simulated,** with one ECU at 7E8. Other protocols can be selected, but the car does not speak them. Real cars often have two ECUs answering the same request (engine and transmission), and the simulator does not do that yet: the phase 2 parser must handle it, and a second ECU is a small addition when its tests need it.
- **The adapter keeps its settings across app connections and reconnects,** as a real one does while it stays plugged in. An `ATSP` protocol is stored, an `ATSP0` is not, and `ATSP00` erases it, as the datasheet describes.
- **Concurrent commands are queued, not interrupted.** A real ELM327 stops what it is doing and prints `STOPPED` when a character arrives during an OBD request, and discards that character. The simulator does not model it: it counts commands that arrive while another is being answered (`overlappedCommands`), so the phase 2 tests can assert that the ELM layer waits for the prompt.
- **Quirks:** drop the first command after a link opens (echo included), ignore `ATAT`, refuse multi-PID requests with `?`, a rate of `NO DATA`, a rate of missing prompts, and a rate of garbage bytes, which are control characters and high bytes that cannot be mistaken for hex.

## Simulator: transports, GPS, recordings and tools (phase 1)

- **`SimTransport` delivers synchronously,** from the scheduled task that produces each piece. A listener then reads the clock at the true moment the piece arrived, which the smoothing pipeline's timestamping needs, and a whole drive can be run inside one `FakeClock.advance`. Real transports are asynchronous; the ELM layer must not depend on either.
- **Link faults come from the scenario and are judged in the car's own time,** so a restarted drive drops the link again at the same point. While the link is out, connecting fails after the connect delay with `unreachable`, and the drop itself is `lost`.
- **Simulated GPS error is a wander, not jitter.** The error of each fix carries over 85% into the next, and its variance follows the conditions: a spell in a street of tall buildings (about one a couple of minutes, a few seconds long) grows it over a few fixes and it dies away afterwards. The accuracy reported is honest: about two fixes in three land within it, which is how a real receiver reports it, so a filter that weighs fixes by accuracy can be tested against this. Standing still, there is no heading.
- **A session log is a text file, one line to an entry:** the time to the millisecond, `>` for sent, `<` for received or `!` for a change of link state, and the text escaped so it stays on one line and reads back exactly (a trailing space is significant). It has a `# tapedash-session v1` first line and `#` header lines for what was recorded. `RecordingTransport` wraps any transport, so it also records a real adapter in a real car after the hardware handoff.
- **Simulator recordings are not kept in git.** `tool/record_sim.dart` writes the same bytes every time for the same options, in about two seconds for all ten scenarios, and they are 0.2 to 2.6 MB each. Real recordings, which cannot be regenerated, go in `recordings/real/`. Until phase 2 there is no OBD stack, so a small scripted client stands in for it: it starts the adapter up, reads the PID support, reads the fault codes, and polls in tiers, one command at a time, and it retries a lost start-up and reconnects after a dropped link. It never reads an answer.
- **`tool/sim_server.dart` listens on 127.0.0.1 unless told otherwise.** An Android emulator reaches the host's loopback as 10.0.2.2, so that is all it needs, and a phone on USB can use `adb reverse`. Serving a phone over the network needs `--host 0.0.0.0` on purpose. It serves one app at a time, as a WiFi adapter does, and the newest connection takes over. It holds a new socket until the transport is up: an app that writes the moment it connects had its first command dropped, which only a real socket run showed, and the test for it fails without the fix. The drive loops by default, as Demo Mode will.
- **The tools run under plain `dart`.** `dart run tool/sim_server.dart` works in this package once `flutter pub get` has run, because everything under `lib/` that they import is free of Flutter.

## Layering (phase 1 additions)

- **`core/` imports nothing else and `sim/` only `core/`,** so nothing the simulator depends on can depend on it, and it stays reusable from `tool/`. CLAUDE.md 6 does not say this; it follows from the simulator being pure Dart and first-class. `SimTransport` and `SimLocationSource` sit in `obd/transport/` and `location/`, one level up, where they belong.
- **The pure directories may not import `ui/`, `app/` or `platform/`,** and `ui/` may not import a transport or sqflite (CLAUDE.md 6, "it never touches transports or the database directly"). The architecture test resolves relative imports as well as package ones.

## Tooling (phase 1 additions)

- **`dart format` rewrites a `\u` escape in a Dart source file into the character itself, including inside a raw string,** which changes what the string means. The session log tests build such characters from code units instead.

## OBD stack: structure (phase 2)

- **The domain code is callback-driven and never awaits.** The client, start-up, poller, session, fault-code service and replay take callbacks and use the injected `Clock` and `Scheduler`. A whole drive, the 30-minute ones of CLAUDE.md 10 included, then runs inside one `FakeClock.advance`, in order, and gives the same readings every time. Futures would have needed the real event loop between steps and made the order depend on microtask scheduling. `SimTransport` delivers inside the call that caused the delivery, and real transports do not, so the whole stack is also run over `AsyncTransport`, a test double that delivers a microtask late, to show that nothing relies on it.
- **`Observable` is our own 60 lines, not `ValueListenable`.** CLAUDE.md 5 says to use `ValueNotifier` and `ValueListenable`, and those live in the Flutter package, which the pure directories may not import (CLAUDE.md 6). `Observable` has the same shape, a `value` with `addListener` and `removeListener`, so a widget wraps one in a line in phase 3a. It notifies at the moment of a change, and only if the value changed, and a listener may remove itself while it is being called. This departs from the wording of CLAUDE.md 5 to keep the layering rule of CLAUDE.md 6.
- **`Sensor` and `Reading` know nothing of PIDs.** `VehicleState` is built on what the car measures, and the PID table maps onto sensors, so a recording, a simulation or a speed from GPS can feed the same state.
- **The session owns the layers, and a page asks for what it needs.** `ObdSession` owns one client, and builds the start-up, the poller and the fault-code service each time it connects. What is polled is a lease (`ObdSession.demand`): a page or trip recording asks for PIDs at a tier and gives them back, and the lease survives a reconnect. Nothing else touches the transport.
- **One ECU is assumed.** The poller asks for one response (`010C1`) and the fault-code service reads one ECU's answer. The simulator has one ECU at 7E8, and so does the third-party emulator's scenario. If two answer the same request, whichever answers first is read, which should be the engine ECU because its arbitration id is the lowest. That is unchecked, and a real car may show that all of them have to be read.

## OBD stack: the ELM327 layer (phase 2)

- **An unreadable reply is a failure, never a guess.** A line that is not hex, or a multi-frame reply with a frame missing, gives no message and the failure `garbled`, so noise cannot become a wrong reading. Frames are put in order by their index, which wraps after `F`, and cut to the length in the header line. There are 17 failures: the adapter's own error strings, and `timeout`, `disconnected` and `garbled`.
- **One command is in flight, and the reply ends at the `>`.** If a reply looks complete and its prompt does not come, the client waits 250 ms more, takes the reply, and counts a missing prompt. After a timeout it pauses 100 ms before the next command, in case the adapter is still talking, and a reply that turns up late is skipped, not taken for the next command's, because the client says which answer it expects (`expectPrefix`, `acceptPrefixes`). Timeouts are 1.5 s for a request, 2 s for a command, 4 s for a reset and 12 s for a protocol search. They are assumptions until a real adapter has been seen.
- **A reading is stamped at the middle of the time until the first data line, not until the prompt.** That is DESIGN.md 5.2's "receipt minus half the round trip", with the round trip ending when the answer starts. The prompt comes 25 to 40 ms after the car answered with adaptive timing, and after the whole 200 ms timeout on a clone that ignores it, so timing to the prompt would stamp a reading later by an amount that has nothing to do with when the car read it.
- **The response-count digit is added to requests on CAN, and only there.** A clone that ignores `ATAT` otherwise waits out its whole 200 ms timeout for a second answer after every request, which caps a poll of single PIDs at about 3 Hz. With the digit it finishes at the first answer. It is sent only when the detected protocol is CAN (6 to 9), the one family the simulator speaks. On other protocols nothing about it has been checked, so those get the plain request. Unverified on hardware.
- **Batching is at most 6 PIDs, only on CAN, and has three ways out.** A `?` for a batched request is the adapter saying it does not know one, and batching stays off for the rest of the session. Any other failure of a batch makes the next 6 requests single, which also fetches what the batch failed to bring, and 3 such failures in a row switch batching off for 60 seconds before it is tried again. Compatibility mode, with no batching and 40 ms between requests, is switched on when start-up needed 3 retries (CLAUDE.md 8.1).
- **Start-up tells a car that says no from an adapter that fails.** `UNABLE TO CONNECT`, `NO DATA`, `CAN ERROR` and `BUS INIT: ...ERROR` after the adapter is set up mean the car is not answering, which is the ignition being off, and the session waits for it. Timeouts, garbled replies, `STOPPED` and `BUFFER FULL` may be noise, and are retried up to twice before start-up gives up. `LV RESET` restarts from `ATZ`, once. `ATH0` and the protocol setting are essential, because the parser cannot read headers and nothing works without a protocol, so an adapter that answers `?` to either is incompatible and the session stops. `ATE0`, `ATL0`, `ATS0` and `ATAT1` are best effort, because the parser copes with echo, linefeeds and spaces anyway.
- **The protocol is remembered per adapter** (`AdapterMemory`, CLAUDE.md 8.1). It is set directly next time, with `ATSP0` as the fallback if the car does not answer on it. It is in memory only for now.
- **Supported-PID discovery retries its later ranges, and says when it could not finish.** A single `NO DATA` for the range that starts at `0x20` left `2F` and `42` unknown for the whole session on a flaky adapter, and nothing showed it. Later ranges are now retried up to twice, `DiscoveryResult.incomplete` says when one still failed, and start-up adds a warning. The first range is not retried by discovery: a failure there is the car's answer, and start-up classifies it.

## OBD stack: polling and the vehicle state (phase 2)

- **Three tiers, and the PID read longest ago goes first.** Fast (every cycle) is RPM, speed and throttle, medium (every second) is load and the fuel source (`5E`, else `10`, else `0B`), and slow (every four seconds) is coolant, intake air, fuel level and voltage, as in CLAUDE.md 8.2. Of the PIDs due, the one read longest ago goes first, judged by a counter of reads and not by time, because PIDs due together have the same timestamp and a tie broken by PID number let the low ones win every round. A PID the car does not answer is asked again after 0, then 100 ms doubling to 2 s, so it cannot starve the others.
- **The poller asks only for what the car has and something wants.** Support comes from discovery, and demand from leases: the standard tiers, plus whatever a page or trip recording adds, such as the fuel source moving to the fast tier while a trip is recorded.
- **Health is two separate things.** Three requests in a row that the car said no to make the ECU silent, which the session takes as the ignition being off and waits. Five in a row that the adapter did not answer, or answered with noise, make the adapter failing, and the session closes the link and reconnects. They are told apart because they need opposite responses.
- **The poller stops itself on a `disconnected` reply,** and the session starts a new one when the link is back. Without that, a poller whose transport had gone spun in a loop of failed requests.
- **Stale is per sensor.** DESIGN.md 5.2 says no sample for 1.5 s is stale. That fits RPM, speed and throttle, which are read every cycle. Load, MAP, MAF and fuel rate are read every second and go stale at 3 s, and coolant, intake air, fuel level and voltage are read every four seconds and go stale at 12 s (`Sensor.staleFactor`). With a flat 1.5 s the slow ones were stale most of the time, and DESIGN.md's stale styling, a fade to grey, would have been on nearly every small gauge nearly all the time. DESIGN.md was silent because it assumed every value is read every cycle.
- **The outlier check judges a change over at least 100 ms.** The timestamps of samples are estimates, and two samples 5 ms apart that differ by a whole km/h are not a change of 200 km/h a second. A reading that implies an impossible change (10,000 rpm/s, or 15 km/h in 100 ms) is held back, and is accepted with the one before it if the next reading confirms it. Otherwise it is dropped and counted (`rejectedReadings`).
- **Speed is smoothed with an exponential average of one second, and acceleration comes from the smoothed speed.** The car reports whole km/h, and each step is 0.28 m/s, so unsmoothed acceleration would jump with every step. The factor is `1 - exp(-dt / tau)` with the real time between samples, so an irregular poll rate does not change the smoothing. `docs/STATUS.md` has what the coach's rule finds in it.
- **Parked is speed 0 for 5 s, or the ignition off. Motion is above 3 km/h.** Between 0 and 3 km/h the mode does not change and the 5-second count starts again, so creeping in a queue is not parked. `engineRunning` is RPM above 400 with the ignition not known to be off.

## OBD stack: the session, and fault codes (phase 2)

- **The connection has the states of DESIGN.md 7.12:** stopped, searching, waiting for the ignition, connected and lost. Lost is a link that was up and went, and the values freeze. Waiting for the ignition is an adapter that is set up whose car does not answer.
- **Reconnecting backs off 1, 2, 4, 8 and then 10 seconds,** and starts from 1 again once connected. While the ignition is off it asks the car once a second and does not repeat the start-up, so the car is found again within a second or two of the key turning.
- **An incompatible adapter stops the session** (`ConnectionProblem.incompatibleAdapter`), and one that never says anything is `adapterSilent`. The session closes the transport itself when it halts, and that close must not be taken for a lost link. In development it was, and an incompatible adapter was reconnected in a loop.
- **Clearing fault codes needs a fresh speed reading of exactly 0.** A stale reading, or none, refuses, so unknown counts as moving. The refusal happens before a byte is sent (CLAUDE.md 8.10). A negative response from the ECU (`7F 04 xx`) is recognised and reported, not waited out.
- **Fault-code descriptions are not bundled yet.** Codes are decoded into P, C, B and U codes, and the JSON of descriptions, whose source has to be permissive and recorded in `assets/dtc/SOURCE.md` (CLAUDE.md 4), comes with the Diagnostics page in phase 5.

## Replay, recordings and the cross-check (phase 2)

- **A replay answers by command, not by the clock.** `ReplayTransport` gives each command the next recorded reply to that same command, in the order recorded, and delivers its pieces at the offsets they had. A recording made by one client at one pace can be played into a client that sends the same commands in another order or at other times, which is what a real car's log needs once the app has changed. A command that is not in the recording gets `?`. An exchange that got no reply, such as a first command a clone lost, stays silent in the replay, so a recording keeps its adapter's misbehaviour. Optionally, the link drops again when it dropped.
- **`tool/record_sim.dart` records the real stack.** The scripted client of phase 1 is gone. An `ObdSession` on a `RecordingTransport` on the simulator makes the traffic, so a recording is what the app really sends. The first replay test of a scripted recording failed because the script never asked which protocol was in use, so the stack, which asks, was not on CAN and sent commands the recording did not have, which is the difference between a stand-in and the real thing. All ten logs now take about 10 seconds and 23 MB, and are still not kept in git.
- **The cross-check against a third-party ELM327 ran, as a separate process.** `tool/crosscheck_emulator.dart` runs an `ObdSession` in real time over TCP against Ircama's ELM327-emulator, which is CC BY-NC-SA 4.0 and cannot be mixed into Apache-2.0 code. It was installed in a throwaway virtual environment outside the repository and started as a process. Nothing of it is in this repository or its history, as code, text or data. The tool has its own small TCP transport, because the app's WiFi transport, with its network guard, is phase 6, and `check_offline.sh` confines sockets under `lib/` to that file. `tool/` is not part of the app.
- **The simulator's multi-frame lines have a space after the colon** (`0: 49 02 ...`) whatever the spaces setting, as the emulator prints them. The datasheet's examples show it with spaces on. The golden fixtures were updated, and the parser reads both this and a last line that is not padded.
- **The simulator's `Elm327Reply` and `Elm327Chunk` became `AdapterOutput` and `AdapterChunk`,** because the client's `Elm327Reply`, which carries the timing and the failure, is the one the rest of the app sees.
- **Deferred on purpose:** trying a batch without the count digit after the adapter refuses one with it (the emulator did), until a real adapter shows a need; reading more than one ECU, for the same reason; and keeping `AdapterMemory` on disk, which belongs to the app's service wiring in phase 3b.

## Testing (phase 2)

- **New components were mutation-checked by hand.** After a component's tests passed, a deliberate bug went in (an off-by-one, a dropped guard, a swapped comparison), and the tests had to fail. At least one test passed for the wrong reason: a fault-code test for a negative response, which would have passed by timing out. It was tightened. This is a habit and not a gate.

## Fonts (phase 3a)

- **Fetched once from a pinned `google/fonts` commit** (`23e54b51ddffbc7713c583748e3bd86f62b1fa4a`), not from each font's own upstream repository, so one commit hash and one set of SHA-256 hashes cover all three families' current release cut. `tool/subset_fonts.sh` re-downloads from that commit and refuses to proceed if a file's hash has changed, so a rebuild is reproducible and a compromised mirror cannot silently swap a font in. This is dev-time only (CLAUDE.md 1); nothing is fetched by the app.
- **Saira's axes are narrowed before subsetting, not after.** `fonttools`' variable-font instancer has to run on the already-subset glyph set, because instancing first leaves the subsetter looking for variation data on glyphs it has already dropped and it errors (`KeyError` on a glyph like `bracketleft.ss02`). `tool/subset_fonts.py` subsets to the character set first, then narrows `wght` to 300-800 and `wdth` to 100-125.
- **The rupee sign comes from Saira in Barlow text too.** Barlow's OFL cut has no ₹ (U+20B9); Saira's does, and it is drawn to match Saira's numerals, which is what money always sits next to. Every Barlow text style lists Saira, and only Saira, as its `fontFamilyFallback`, so a ₹ inside a Barlow label (`₹ THIS TRIP`) renders from Saira and nothing else ever substitutes silently. `test/design/fonts_test.dart` checks the fallback list and that Barlow really has no ₹ of its own, so a future subset that adds one would be caught changing behaviour unexpectedly.
- **No hinting is kept.** Android's text renderer does not run TrueType bytecode, so instructions are dead weight; `fonttools.subset` drops them explicitly rather than relying on subsetting to remove them as a side effect.

## Design system: tokens and theme (phase 3a)

- **`TapePalette` resolves a livery in a mode once**, rather than every component computing "is this Daylight, and does this livery's accent reach 10:1" for itself. DESIGN.md 4.4's Daylight and Night rules (halos off/halved, strokes +50%, `ink.dim`->`ink.mid`, labels to `ink.bright`, an accent under 10:1 giving way to `ink.bright` for numerals while keeping the accent for fills and needles, the rupee sign switching `money.deep`->`money.core`) are specific enough, and touch enough colours, that writing them once and testing that one place against every livery x mode combination (`test/design/theme_test.dart`) was the only way to be sure they were even internally consistent.
- **Contrast is computed, not eyeballed.** `Contrast.ratio` is a standard WCAG relative-luminance calculation; DESIGN.md 11's numbers (7:1 primary, 4.5:1 other text, 10:1 Daylight primary, with `critical` and `stale` exempted from the 7:1/10:1 floor but not the 4.5:1 one) are asserted against every token pair actually used for text, in every livery and mode, rather than checked by looking at a render.
- **The mode controller's window is exactly the thresholds DESIGN.md 4.4 states** (enter Daylight above 5,000 lux, leave below 2,000; enter Night below 20, leave above 60; both need 10 s), with no smoothing beyond that dwell. A shorter or additional filter was considered and dropped: the spec already asks for hysteresis by having different enter and leave thresholds, and stacking a second filter on top would make the transition point unpredictable from the spec's own numbers.

## Motion core (phase 3a)

- **One clock, two implementations, same interface.** `VsyncMotionClock` ticks from a real `Ticker`; `ManualMotionClock` is stepped by hand. Every spring, phosphor bank and smoothed signal takes a `MotionClock` and does not know which it has, which is what lets a widget test drive a spring through an exact sequence of frames and assert on the result, the same way `FakeClock` lets the OBD stack's tests run a drive in no time (CLAUDE.md 5, "Time").
- **A frame is clamped to 50 ms, matching DESIGN.md 5.9 exactly**, and the clamp lives in the clock, not in each spring: a spring given a 3-second dt because the app was backgrounded would otherwise jump straight to its target, which is exactly the "nothing teleports" rule (DESIGN.md 2) being broken by the one component responsible for guaranteeing it never is.
- **`SmoothedSignal` tracks noise as a run of sign flips of the instantaneous rate (two in a row), not a variance or a threshold on the rate's own size.** A steady climb read in whole km/h steps every 100 ms has an instantaneous rate that is not smooth (it is zero for four samples, then a jump), but it never changes sign, so it is not flagged noisy; two flips in a row is specifically the pattern a value oscillating around a true reading produces. A `noiseFloor` (1 unit/s) keeps quantisation of an unmoving value from counting: a signal alternating by 0.5 in its last decimal has a rate under the floor and is never judged by its sign.
- **Lead compensation defaults to zero and is capped at 150 ms, exactly DESIGN.md 5.2's numbers,** because it is explicitly "tuned after the hardware handoff" there — phase 3a has no real adapter latency to tune it against, so the only correct default is off.

## Render primitives (phase 3a)

- **One glyph atlas per (size, weight, density) triple, not per livery.** A sprite is drawn white and tinted at draw time with `BlendMode.modulate`, so ION, EMBER and MONO (all Saira, different weights) share atlases whenever their weight and size happen to match, and a livery switch never rebuilds one. Only the weight (which changes the glyph outlines) and the density (which changes the raster) force a new atlas.
- **A halo atlas is a second, separate atlas built with a nonzero `glowSigmaLp`,** not a blurred copy of the crisp one taken at paint time. `MaskFilter.blur` is baked into the image once when the atlas is built (DESIGN.md 9.3's "never blur at runtime"); Tier 1 asks for this atlas at half resolution (`GlyphAtlasSpec.resolution`), which is a smaller image and a coarser blur, not a smaller draw of the full-resolution one.
- **The grain tile compensates the canvas colour it sits over, not the other way round.** Grain is additive white speckle at a small average opacity; laid directly over the `void`/`carbon.900` gradient, the *result* averages brighter than the token colours by roughly the grain's own opacity. `TapeBackdrop` darkens the gradient's stops by that amount first (`_beneathGrain`, solving `base + grain * (1 - base) = target` for `base`), so the void reads as the void token on average, with grain, rather than the void token before grain is added. DESIGN.md does not say the two combine this way; recorded here since it affects what `void` actually renders as everywhere the backdrop is used.
- **The seven-segment renderer draws all seven segments of a digit as separate sprites, each with its own phosphor level, every frame** — never a "digit changed, cross-fade the whole glyph" tween. This is what makes 1 -> 7 (which shares segments b and c) hold those two segments lit throughout while only a, d, e, f, g move, matching a real VFD and DESIGN.md 6.17's "crossfades segment by segment" literally, not as a metaphor for a glyph-level fade.

## Icon set (phase 3a)

- **Icons are a tiny path DSL (`M`/`L`/`Z`/`O`/`D`/`Q` plus numbers), parsed once into typed ops and cached per enum value**, rather than each icon being a `CustomPainter` or a list of `Offset` literals in Dart. A malformed command is a `FormatException` at first use (caught by `test/design/icons_test.dart`'s "every icon parses" test) rather than a silently-missing line, and the 24-unit-grid and axis-or-45-degree rules (DESIGN.md 4.8) can be checked mechanically against the parsed ops instead of by eye.

## Fidelity (phase 3a)

- **A tier's cost is estimated as a fixed multiple of another tier's** (Lite 0.6x, Balanced 1x, Full 1.7x, relative to Balanced), not measured by actually rendering at every tier during the cold open. DESIGN.md 9.2 only asks the detector to run once, at the tier the cold open happens to draw at, and infer the others; the multiples are estimates pending real-device tuning after the hardware handoff (CLAUDE.md 13, phase 7), and are named as such in the code and in the phase 3a review package.
- **The governor's window is one second, not DESIGN.md 9.2's literal silence on the point.** A longer window was tried first and found to keep counting a bad stretch of frames as "still over budget" for the window's length after the stretch had actually ended, which the governor's own test for "a good stretch resets the count" caught. One second means the 90th-percentile judgement is never more than a second stale.

## Design Lab and app shell (phase 3a)

- **The Lab opens from a dev button on the void screen, not from CLAUDE.md 9's long-press debug overlay,** because that overlay does not exist yet — there is nothing to long-press on a screen that is still just `void`. The button's visibility already follows the rule the overlay will eventually want (debug and profile builds, or an explicit `--dart-define=TAPEDASH_DEV=true` in release), so moving the Lab's entry point behind the real overlay later is a visibility check moved, not a new one designed. Open question for the human, in the phase 3a review package.
- **`capture-all`'s image renderer is injectable** (`DesignLab.captureRenderer`), defaulting to the real `RenderRepaintBoundary.toImage`-based one. Found necessary, not chosen upfront: driving the real renderer through the sweep's `setState` -> `endOfFrame` -> `toImage` loop inside one `tester.runAsync` block never completes under `flutter_test` — `toImage()`'s completion callback does not fire once a `tester.pump()` has run earlier in the same `runAsync` zone. This is a `flutter_test` limitation, not an application bug (the whole Lab, capture-all included, was run and screenshotted on a real API 24 emulator without issue); recorded in the shell-quirks memory so it is not rediscovered. The sweep's own logic is tested with a fake renderer that resolves instantly; the real renderer is tested separately, on an already-settled tree, with no `pump()` sharing its `runAsync` block.
- **`capture-all` writes to the system temp directory**, standing in for a real app-storage path. CLAUDE.md 5's device-feature list has no storage-path decision yet, and adding a platform-channel method for one felt like scope creep on a phase about the design system, not the device channel. Open question for the human on whether it is worth adding now, in the phase 3a review package.
- **The design lint's scope is `lib/ui` plus `lib/app/app.dart` by name, not all of `lib/app`.** Widening it to the whole directory first and running it found `lib/app/demo_drive.dart`'s poll-loop interval (`Duration(seconds: 2)`, how often the loop checks whether the simulated drive has finished) flagged as a "duration literal outside tokens" violation. That is service wiring, not a design constant, and DESIGN.md 13.1's rule is specifically about the look and feel the design system controls; only `app.dart`, which composes the actual UI shell, is held to it.
- **`DemoDrive` mirrors `ObdSession`'s own reconnect and demand machinery rather than wrapping it opaquely**, exposing `scenario`, `profile`, `running` and `description` as `Observable`s alongside the `VehicleState` it fills. This is so phase 3b's Demo Mode picker (DESIGN.md 7.6) can show and change the running scenario without reaching into the session itself, and so the same `DataSource` interface can be satisfied later by a thin wrapper around a real `ObdSession` with nothing scenario-shaped in it.

## HUD (phase 3b)

- **The HUD draws under its own theme: a `hud` livery** (`Liveries.hud(HudColor)`), the user's colour as the accent, Bold numerals, no halo, so the existing numeral components work unchanged instead of a parallel set. `TapeThemeData` and `TapePalette` equality now include the accent colour, since two HUD colours share one livery id and a colour change must still notify the widgets below.

## Brand (phase 3b)

- **The icon is generated by our own script (`tool/make_brand.py`, Pillow, dev-time only), not by `flutter_launcher_icons`.** The adaptive icon is plain vector drawables (no dependency, no raster foreground), and the script writes the legacy PNGs for API 24-25 from the same shape description, so the two cannot drift. ## Fuel, money and trips (phase 4)

- **A closed throttle is where the car reads it at idle, not 0.** PID 11 is the absolute throttle position, which reads 10 to 20% with the throttle shut (the simulator's reads 12%). CLAUDE.md 8.4's "throttle at 0" therefore never matched, and air-based estimates counted a coast with the fuel cut as burning: +5.7% on the sporty manual in city driving. `FuelEstimator` now learns the closed reading (the lowest throttle seen while idling) and judges the cut from it, falling back to 2% until the car has idled. After the fix every petrol profile is within about 2% of the truth on every scenario.
- **Speed-density uses an rpm-shaped VE, not a flat 0.85.** A flat 0.85 over-counts fuel at idle by ~20% (the simulator's VE is 0.70 at idle, 0.85 at 2000 rpm), which put idle cost 17% high on a jam. `FuelConstants.volumetricEfficiencyShape` is a generic naturally-aspirated shape, 1.0 at 2000 rpm; the level is still 0.85 and is what calibration corrects. **Caveat:** the simulator's curve and this shape are both "a typical road engine", so agreement in tests proves the machinery, not accuracy on a real car; real cars are expected to need the calibration factor. Pass an empty shape for a flat VE.
- **Air-based estimates during a suspected fuel cut are 0**, not the reported air converted to fuel (air still flows in a cut). 5E is never overridden.
- **A gap in the estimates over 30 s is not integrated at all; a gap over 3 s is filled with the average of its two sides and flagged.** Burning nothing is a smaller error than making fuel up, and a reconnect never brings a spike.
- **Rupee blocks go to the bucket with the most spend not yet in a block,** not to the bucket of the sample that crossed the whole rupee. The latter favoured whichever bucket was burning at the crossing (1.8 blocks off on a jam trip); this keeps each bucket within one block of its cost.
- **Hard-acceleration fuel waits, in order, for the detector.** A hard acceleration is only known after 1 s (or 2 s of throttle), so the fuel from those first moments is held and put in the hard bucket if the event confirms, or in normal driving if it does not.
- **The fill-up ledger counts the raw estimate** (before calibration), since the correction is what is being worked out; a factor from a fill-up needs at least 1 L on each side and a ratio between 0.4 and 2.5 (further out means the app missed trips, and is not used).
- **The engine is judged off from the connection status, not the last voltage:** the car stops answering (waiting for ignition), or answers with rpm 0 and under 13 V. A lost adapter link says nothing about the engine, so the trip carries on (and ends after 5 minutes of nothing).
- **The fuel PID moves to the fast tier while a trip is recorded** (`RecordingDemand`): 5E, MAF or MAP, whichever is the source, or all three until one is chosen.
