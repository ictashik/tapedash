# Decisions

A short running log of choices and the reasons for them, newest last. It includes design decisions where DESIGN.md is silent, and every dependency (license and reason, per CLAUDE.md 5).

## Project

- **License: Apache-2.0.** The user's choice, and the one CLAUDE.md recommends. It is permissive, has a patent grant and is accepted by F-Droid. Not GPL, which would bind the whole app.
- **Application ID: `io.github.ictashik.tapedash`.** The `io.github.<user>.<repo>` form is the usual one for an open-source app without its own domain. The GitHub handle is taken from the git identity's noreply address and has not been confirmed, and there is no remote yet. Renaming is a few lines until the first release and effectively impossible after it, so confirm it before then.
- **No remote.** The repository is local only. Nothing is pushed without the user's explicit say-so (CLAUDE.md 2).

## Toolchain

- **Flutter 3.44.1 stable, Dart 3.12.1.** Flutter stable only (CLAUDE.md 3). Android Gradle Plugin 9.0.1, Kotlin 2.3.20 and Gradle 9.1.0 come from that Flutter version's template. Needs JDK 17.
- **minSdk 24 and targetSdk 36 are Flutter's own defaults** (`flutter.minSdkVersion`, `flutter.targetSdkVersion`). Flutter's default minSdk is already Android 7.0, so there is nothing to override. We never raise it for convenience.
- **CI builds only `armeabi-v7a` and `arm64-v8a`**, the two ABIs we ship. A plain `--split-per-abi` release build also produces an x86_64 APK we do not want.

## Android

- **Launch window is `void`, in one theme only.** TapeDash is always dark (DESIGN.md 4.1), so there is no `values-night`. The launch drawable, `NormalTheme` and the Android 12+ splash background are all the `tapedash_void` colour, and `test/unit/platform/launch_theme_test.dart` fails if any of them drifts from `TapeColors.voidColor` or turns white. The default Flutter template used white and `?android:colorBackground`, which is what causes a white flash.
- **`android:allowBackup="false"`.** Android Auto Backup uploads app data to the user's Google account, and TapeDash is strictly offline. Trips leave the phone only through the CSV export.
- **Landscape comes from the manifest alone** (`sensorLandscape`, both directions). It works even with the phone's rotation lock on and avoids a portrait frame at launch, so there is no `SystemChrome` orientation call.
- **No permissions are declared yet.** Each one is added together with the feature that needs it, and must be on the allowed list in CLAUDE.md 4.
- **`uses-material-design: false`.** Material widgets and icons are banned (DESIGN.md 13.1), so the Material icon font is not bundled.

## Code

- **`TapeColors.voidColor`**, not `TapeColors.void`: `void` is a reserved word in Dart. Other tokens keep the DESIGN.md name with dots removed (`carbon900`, `etchStrong`) when they arrive in phase 3a.
- **`lib/main.dart` uses `WidgetsApp`**, not `MaterialApp`, so no Material code is linked in at all.

## Device features

- **`DeviceFeatures` is an interface**, with `DeviceChannel` (platform channels to `DeviceChannel.kt`) and `FakeDeviceFeatures` behind it. Code that needs the screen, battery or sensors takes the interface, so Daylight and Night switching and the phone-health logic can be tested headlessly.
- **One shared stream per sensor.** A Flutter `EventChannel` has one native handler, so a second `receiveBroadcastStream()` would silently take the sensor from the first listener. The streams are built once, and the sensor is only registered while something listens.
- **Brightness has a floor.** Dart clamps the level to 0..1 and rejects NaN, and the Android side never goes below 0.01, since some phones treat 0 as backlight off, which would blank the dash. The design floors (12% at night, 20% for the HUD) are policy for the brightness controller and are not enforced here.
- **Accelerometer axes are remapped in Dart.** Android reports the sensor in the phone's own axes, not the screen's. The Android side sends `[x, y, z, displayRotation]` untouched, and Dart turns it into screen axes (x right, y up the screen, z out of it), so the mapping is unit-tested and CI covers it. It matters because the app is landscape-only, so a phone held upright is still drawn rotated. Checked on emulators by rotating the emulated phone: with the display following the phone into either landscape, gravity reads +9.8 on screen y whichever rotation the OS reports.
- **Immersive mode** uses `WindowInsetsController` on Android 11+ and the legacy `systemUiVisibility` flags below, and is re-applied when the window regains focus. On Android 4.4 to 10 the OS shows a one-time "Viewing full screen" notice the first time an app goes immersive. It cannot be suppressed, and one tap on "Got it" dismisses it for good. Expect it on old phones.
- **Startup never waits on the window calls.** If hiding the bars or keeping the screen on fails, that is logged and the app starts anyway. Other errors, which would be bugs, are not swallowed.
- **Launch flash cannot be measured on emulators.** With the launch colour set to solid red, no red frame appears on either an Android 7.0 or an Android 16 emulator, so an emulator recording cannot show a white flash, broken or fixed. The launch resources are guarded by `launch_theme_test.dart` instead, and a check on a real phone is part of the hardware handoff.

## Simulator: the car (phase 1)

- **The physics is a Willans-line engine, not a lookup table.** Throttle sets manifold pressure through an orifice, air follows the speed-density formula of CLAUDE.md 8.4, fuel is air over the air-fuel ratio, and torque is the fuel's energy less pumping, friction and accessory losses. So MAF, MAP, load and fuel rate are consistent with each other by construction, which is what the fuel estimators have to be tested against. A petrol engine controls air first, and a diesel controls fuel first with a smoke limit. Fuel is cut on the overrun above 1,500 rpm while the air keeps flowing, so MAF stays non-zero with no fuel burnt, which is a trap for estimators.
- **Two powertrains.** A CVT, where engine speed follows the pedal more than road speed, and a manual, where a virtual driver changes gear with hysteresis and a dwell so the gearbox cannot hunt.
- **The physics does not depend on the seed.** Each part draws from its own forked stream, and the seed only changes the reported noise (idle wobble, sensor noise, GPS error). Two runs with different seeds burn exactly the same fuel, so a test can compare any two of them, and turning noise on can never move the ground truth.
- **Ground truth is exact and kept apart from what the ECU reports.** Cumulative fuel, distance, engine-on time, idle time and idle fuel (idle is under 2 km/h with the engine running, CLAUDE.md 8.7), and a log of every scripted hard-acceleration and hard-braking event. It is recomputed independently from the snapshots in the tests.
- **Deviations from the wording of CLAUDE.md 7.1, on purpose.**
  - Braking is 7.5 m/s2 plus drag and engine braking, about 8 m/s2 at most, and grip limits a launch to 0.36 g. The spec says "up to about 8".
  - Coolant reaches 85 C after 8 minutes of city driving and is then held at about 90 C by the thermostat, as specified, but idling warms an engine far more slowly, because a warm-up needs load: `cold_start_idle` is at 51 C after its 5 minutes. The spec's "8 to 10 minutes" holds for a drive, not for idling.
- **A scripted driver inverts the model.** It asks the vehicle model which pedal gives a wanted acceleration (`pedalForAcceleration`), so a speed is held smoothly and a stop is reached without overshoot. These what-if questions must never change the car, and must never trigger a gear change: an early version's what-if returned the clutch-out acceleration and made the driver slam the pedal to 1 and kick down for real. They are tested to change nothing.
- **Hard driving has to survive the app's own smoothing.** The coach smooths speed over about a second before it looks at acceleration (CLAUDE.md 8.8), which hides an acceleration that only just clears its threshold or does not last. A first version of the hard style passed a peak-over-threshold check and the app's detector found 6 of 12 scripted events. The hard style now asks for 3.6 and 5.0 m/s2 and the aggressive route runs at 64 km/h, and a test applies the app's rule to whole km/h samples at 10 Hz. The phase 5 requirement that detected counts match the scripted ones depends on this.
- **`eco_city` is 30% cheaper than `aggressive_city`** over the same 4.5 km (0.372 L against 0.535 L), with the same waits at the signals, so the saving is in the driving. The spec asks for at least 15%.
- **Profiles are approximations, not data from any real car** (CLAUDE.md 7.2). PID 01 is in none of the PID lists because every OBD-II ECU has it; the simulator always adds it.

## Simulator: the adapter (phase 1)

- **The byte format comes from the ELM327 datasheet, and the golden fixtures are written by hand from it.** The datasheet's own examples are the fixtures: `0100` giving `41 00 BE 1F B8 10`, the VIN as `014` and `0: 49 02 01 31 44 34`, and `01 04 05 0B 0C` as `00A` with the last line padded with zeros. All sixteen combinations of echo, linefeeds, spaces and headers are written out as literal strings, so the simulator is checked against the spec and not against itself.
- **The datasheet is written for a person at a terminal, so it leaves some byte-level conventions open.** These follow what real adapters are known to send, and **none of them has been checked against hardware**:
  - every reply ends with a blank line and then `>`, so `OK` is `OK\r\r>` (or `OK\r\n\r\n>` with linefeeds on);
  - after `ATZ` or `ATWS` the banner is preceded by two `\r`;
  - with spaces on, a data line ends with a space, as in `41 0C 1A F8 \r`;
  - a multi-frame line is `0:` and a space, then the bytes;
  - a lone carriage return repeats the last command;
  - `ATDP` names the CAN protocols as `ISO 15765-4 (CAN 11/500)`, with `AUTO, ` in front when it may search;
  - what the adapter prints for a fixed protocol the car does not speak: `BUS INIT: ...ERROR` for the K-line protocols, `NO DATA` for J1850 and 29-bit CAN, `CAN ERROR` for the other bit rates.
  The app's parser has to be tolerant of all of these anyway (CLAUDE.md 8.1), and the first real adapter session should be compared against them (see the hardware handoff notes in STATUS.md).
- **Behaviour was cross-checked against Ircama's ELM327-emulator by reading its source.** That project is CC BY-NC-SA 4.0, which is non-commercial and share-alike and so cannot be mixed into Apache-2.0 code. It was read for how real adapters are seen to behave, and nothing from it is in this repository, as code, text or data, and it is not a dependency. The optional cross-check in CLAUDE.md 7.5, running our parser against its output over TCP, is for phase 2 and needs the same care.
- **Adapter timing is an assumption, because the datasheet gives no figures:** a reset takes 0.8 s, finding a protocol 2.4 s (0.4 s if the stored one is right), an unreachable car 5 s to give up, the ECU answers in 20 ms, and adaptive timing waits 40 ms (AT1) or 25 ms (AT2) after the answer. Without adaptive timing, or on a clone that ignores it, the adapter waits its whole `ATST` timeout (200 ms) unless the request ends with a response-count digit. On the Bluetooth clone preset that makes a request without the digit about 300 ms and one with it about 100 ms, so three fast-tier PIDs asked one at a time without the digit are about 1 Hz. It is the reason the ELM layer should add the digit, or batch.
- **`AdapterQuirks.latency` is the link's round trip, and the adapter's own time comes on top of it.** The car is asked in the middle of the round trip, so a value is as old as half the latency by the time it arrives, and the app's timestamping at the midpoint of a request is exactly right. `Elm327Device` does this; `Elm327Simulator` itself has no notion of the link.
- **Only ISO 15765-4 CAN (11-bit, 500 kbaud, protocol 6) is simulated,** with one ECU at 7E8. Other protocols can be selected, but the car does not speak them. Real cars often have two ECUs answering the same request (engine and transmission), and the simulator does not do that yet: the phase 2 parser must handle it, and a second ECU is a small addition when its tests need it.
- **The adapter keeps its settings across app connections and reconnects,** as a real one does while it stays plugged in. An `ATSP` protocol is stored, an `ATSP0` is not, and `ATSP00` erases it, as the datasheet describes.
- **Concurrent commands are queued, not interrupted.** A real ELM327 stops what it is doing and prints `STOPPED` when a character arrives during an OBD request, and discards that character. The simulator does not model it: it counts commands that arrive while another is being answered (`overlappedCommands`), so the phase 2 tests can assert that the ELM layer waits for the prompt.
- **Quirks:** drop the first command after a link opens (echo included), ignore `ATAT`, refuse multi-PID requests with `?`, a rate of `NO DATA`, a rate of missing prompts, and a rate of garbage bytes, which are control characters and high bytes that cannot be mistaken for hex.

## Simulator: transports, GPS, recordings and tools (phase 1)

- **`SimTransport` delivers synchronously,** from the scheduled task that produces each piece. A listener then reads the clock at the true moment the piece arrived, which the smoothing pipeline's timestamping needs, and a whole drive can be run inside one `FakeClock.advance`. Real transports are asynchronous; the ELM layer must not depend on either.
- **Link faults come from the scenario and are judged in the car's own time,** so a restarted drive drops the link again at the same point. While the link is out, connecting fails after the connect delay with `unreachable`, and the drop itself is `lost`.
- **Simulated GPS error is a wander, not jitter.** The error of each fix carries over 85% into the next, and its variance follows the conditions: a spell in a street of tall buildings (about one a couple of minutes, a few seconds long) grows it over a few fixes and it dies away afterwards. The accuracy reported is honest: about two fixes in three land within it, which is how a real receiver reports it, so a filter that weighs fixes by accuracy can be tested against this. Standing still, there is no heading.
- **A session log is a text file, one line to an entry:** the time to the millisecond, `>` for sent, `<` for received or `!` for a change of link state, and the text escaped so it stays on one line and reads back exactly (a trailing space is significant). It has a `# tapedash-session v1` first line and `#` header lines for what was recorded. `RecordingTransport` wraps any transport, so it also records a real adapter in a real car after the hardware handoff.
- **Simulator recordings are not kept in git.** `tool/record_sim.dart` writes the same bytes every time for the same options, in about two seconds for all ten scenarios, and they are 0.2 to 2.6 MB each. Real recordings, which cannot be regenerated, go in `recordings/real/`. Until phase 2 there is no OBD stack, so a small scripted client stands in for it: it starts the adapter up, reads the PID support, reads the fault codes, and polls in tiers, one command at a time, and it retries a lost start-up and reconnects after a dropped link. It never reads an answer.
- **`tool/sim_server.dart` listens on 127.0.0.1 unless told otherwise.** An Android emulator reaches the host's loopback as 10.0.2.2, so that is all it needs, and a phone on USB can use `adb reverse`. Serving a phone over the network needs `--host 0.0.0.0` on purpose. It serves one app at a time, as a WiFi adapter does, and the newest connection takes over. It holds a new socket until the transport is up: an app that writes the moment it connects had its first command dropped, which only a real socket run showed, and the test for it fails without the fix. The drive loops by default, as Demo Mode will.
- **The tools run under plain `dart`.** `dart run tool/sim_server.dart` works in this package once `flutter pub get` has run, because everything under `lib/` that they import is free of Flutter.

## Layering (phase 1 additions)

- **`core/` imports nothing else and `sim/` only `core/`,** so nothing the simulator depends on can depend on it, and it stays reusable from `tool/`. CLAUDE.md 6 does not say this; it follows from the simulator being pure Dart and first-class. `SimTransport` and `SimLocationSource` sit in `obd/transport/` and `location/`, one level up, where they belong.
- **The pure directories may not import `ui/`, `app/` or `platform/`,** and `ui/` may not import a transport or sqflite (CLAUDE.md 6, "it never touches transports or the database directly"). The architecture test resolves relative imports as well as package ones.

## Tooling (phase 1 additions)

- **`dart format` rewrites a `\u` escape in a Dart source file into the character itself, including inside a raw string,** which changes what the string means. The session log tests build such characters from code units instead.

## OBD stack: structure (phase 2)

- **The domain code is callback-driven and never awaits.** The client, start-up, poller, session, fault-code service and replay take callbacks and use the injected `Clock` and `Scheduler`. A whole drive, the 30-minute ones of CLAUDE.md 10 included, then runs inside one `FakeClock.advance`, in order, and gives the same readings every time. Futures would have needed the real event loop between steps and made the order depend on microtask scheduling. `SimTransport` delivers inside the call that caused the delivery, and real transports do not, so the whole stack is also run over `AsyncTransport`, a test double that delivers a microtask late, to show that nothing relies on it.
- **`Observable` is our own 60 lines, not `ValueListenable`.** CLAUDE.md 5 says to use `ValueNotifier` and `ValueListenable`, and those live in the Flutter package, which the pure directories may not import (CLAUDE.md 6). `Observable` has the same shape, a `value` with `addListener` and `removeListener`, so a widget wraps one in a line in phase 3a. It notifies at the moment of a change, and only if the value changed, and a listener may remove itself while it is being called. This departs from the wording of CLAUDE.md 5 to keep the layering rule of CLAUDE.md 6.
- **`Sensor` and `Reading` know nothing of PIDs.** `VehicleState` is built on what the car measures, and the PID table maps onto sensors, so a recording, a simulation or a speed from GPS can feed the same state.
- **The session owns the layers, and a page asks for what it needs.** `ObdSession` owns one client, and builds the start-up, the poller and the fault-code service each time it connects. What is polled is a lease (`ObdSession.demand`): a page or trip recording asks for PIDs at a tier and gives them back, and the lease survives a reconnect. Nothing else touches the transport.
- **One ECU is assumed.** The poller asks for one response (`010C1`) and the fault-code service reads one ECU's answer. The simulator has one ECU at 7E8, and so does the third-party emulator's scenario. If two answer the same request, whichever answers first is read, which should be the engine ECU because its arbitration id is the lowest. That is unchecked, and a real car may show that all of them have to be read.

## OBD stack: the ELM327 layer (phase 2)

- **An unreadable reply is a failure, never a guess.** A line that is not hex, or a multi-frame reply with a frame missing, gives no message and the failure `garbled`, so noise cannot become a wrong reading. Frames are put in order by their index, which wraps after `F`, and cut to the length in the header line. There are 17 failures: the adapter's own error strings, and `timeout`, `disconnected` and `garbled`.
- **One command is in flight, and the reply ends at the `>`.** If a reply looks complete and its prompt does not come, the client waits 250 ms more, takes the reply, and counts a missing prompt. After a timeout it pauses 100 ms before the next command, in case the adapter is still talking, and a reply that turns up late is skipped, not taken for the next command's, because the client says which answer it expects (`expectPrefix`, `acceptPrefixes`). Timeouts are 1.5 s for a request, 2 s for a command, 4 s for a reset and 12 s for a protocol search. They are assumptions until a real adapter has been seen.
- **A reading is stamped at the middle of the time until the first data line, not until the prompt.** That is DESIGN.md 5.2's "receipt minus half the round trip", with the round trip ending when the answer starts. The prompt comes 25 to 40 ms after the car answered with adaptive timing, and after the whole 200 ms timeout on a clone that ignores it, so timing to the prompt would stamp a reading later by an amount that has nothing to do with when the car read it.
- **The response-count digit is added to requests on CAN, and only there.** A clone that ignores `ATAT` otherwise waits out its whole 200 ms timeout for a second answer after every request, which caps a poll of single PIDs at about 3 Hz. With the digit it finishes at the first answer. It is sent only when the detected protocol is CAN (6 to 9), the one family the simulator speaks. On other protocols nothing about it has been checked, so those get the plain request. Unverified on hardware.
- **Batching is at most 6 PIDs, only on CAN, and has three ways out.** A `?` for a batched request is the adapter saying it does not know one, and batching stays off for the rest of the session. Any other failure of a batch makes the next 6 requests single, which also fetches what the batch failed to bring, and 3 such failures in a row switch batching off for 60 seconds before it is tried again. Compatibility mode, with no batching and 40 ms between requests, is switched on when start-up needed 3 retries (CLAUDE.md 8.1).
- **Start-up tells a car that says no from an adapter that fails.** `UNABLE TO CONNECT`, `NO DATA`, `CAN ERROR` and `BUS INIT: ...ERROR` after the adapter is set up mean the car is not answering, which is the ignition being off, and the session waits for it. Timeouts, garbled replies, `STOPPED` and `BUFFER FULL` may be noise, and are retried up to twice before start-up gives up. `LV RESET` restarts from `ATZ`, once. `ATH0` and the protocol setting are essential, because the parser cannot read headers and nothing works without a protocol, so an adapter that answers `?` to either is incompatible and the session stops. `ATE0`, `ATL0`, `ATS0` and `ATAT1` are best effort, because the parser copes with echo, linefeeds and spaces anyway.
- **The protocol is remembered per adapter** (`AdapterMemory`, CLAUDE.md 8.1). It is set directly next time, with `ATSP0` as the fallback if the car does not answer on it. It is in memory only for now.
- **Supported-PID discovery retries its later ranges, and says when it could not finish.** A single `NO DATA` for the range that starts at `0x20` left `2F` and `42` unknown for the whole session on a flaky adapter, and nothing showed it. Later ranges are now retried up to twice, `DiscoveryResult.incomplete` says when one still failed, and start-up adds a warning. The first range is not retried by discovery: a failure there is the car's answer, and start-up classifies it.

## OBD stack: polling and the vehicle state (phase 2)

- **Three tiers, and the PID read longest ago goes first.** Fast (every cycle) is RPM, speed and throttle, medium (every second) is load and the fuel source (`5E`, else `10`, else `0B`), and slow (every four seconds) is coolant, intake air, fuel level and voltage, as in CLAUDE.md 8.2. Of the PIDs due, the one read longest ago goes first, judged by a counter of reads and not by time, because PIDs due together have the same timestamp and a tie broken by PID number let the low ones win every round. A PID the car does not answer is asked again after 0, then 100 ms doubling to 2 s, so it cannot starve the others.
- **The poller asks only for what the car has and something wants.** Support comes from discovery, and demand from leases: the standard tiers, plus whatever a page or trip recording adds, such as the fuel source moving to the fast tier while a trip is recorded.
- **Health is two separate things.** Three requests in a row that the car said no to make the ECU silent, which the session takes as the ignition being off and waits. Five in a row that the adapter did not answer, or answered with noise, make the adapter failing, and the session closes the link and reconnects. They are told apart because they need opposite responses.
- **The poller stops itself on a `disconnected` reply,** and the session starts a new one when the link is back. Without that, a poller whose transport had gone spun in a loop of failed requests.
- **Stale is per sensor.** DESIGN.md 5.2 says no sample for 1.5 s is stale. That fits RPM, speed and throttle, which are read every cycle. Load, MAP, MAF and fuel rate are read every second and go stale at 3 s, and coolant, intake air, fuel level and voltage are read every four seconds and go stale at 12 s (`Sensor.staleFactor`). With a flat 1.5 s the slow ones were stale most of the time, and DESIGN.md's stale styling, a fade to grey, would have been on nearly every small gauge nearly all the time. DESIGN.md was silent because it assumed every value is read every cycle.
- **The outlier check judges a change over at least 100 ms.** The timestamps of samples are estimates, and two samples 5 ms apart that differ by a whole km/h are not a change of 200 km/h a second. A reading that implies an impossible change (10,000 rpm/s, or 15 km/h in 100 ms) is held back, and is accepted with the one before it if the next reading confirms it. Otherwise it is dropped and counted (`rejectedReadings`).
- **Speed is smoothed with an exponential average of one second, and acceleration comes from the smoothed speed.** The car reports whole km/h, and each step is 0.28 m/s, so unsmoothed acceleration would jump with every step. The factor is `1 - exp(-dt / tau)` with the real time between samples, so an irregular poll rate does not change the smoothing. `docs/STATUS.md` has what the coach's rule finds in it.
- **Parked is speed 0 for 5 s, or the ignition off. Motion is above 3 km/h.** Between 0 and 3 km/h the mode does not change and the 5-second count starts again, so creeping in a queue is not parked. `engineRunning` is RPM above 400 with the ignition not known to be off.

## OBD stack: the session, and fault codes (phase 2)

- **The connection has the states of DESIGN.md 7.12:** stopped, searching, waiting for the ignition, connected and lost. Lost is a link that was up and went, and the values freeze. Waiting for the ignition is an adapter that is set up whose car does not answer.
- **Reconnecting backs off 1, 2, 4, 8 and then 10 seconds,** and starts from 1 again once connected. While the ignition is off it asks the car once a second and does not repeat the start-up, so the car is found again within a second or two of the key turning.
- **An incompatible adapter stops the session** (`ConnectionProblem.incompatibleAdapter`), and one that never says anything is `adapterSilent`. The session closes the transport itself when it halts, and that close must not be taken for a lost link. In development it was, and an incompatible adapter was reconnected in a loop.
- **Clearing fault codes needs a fresh speed reading of exactly 0.** A stale reading, or none, refuses, so unknown counts as moving. The refusal happens before a byte is sent (CLAUDE.md 8.10). A negative response from the ECU (`7F 04 xx`) is recognised and reported, not waited out.
- **Fault-code descriptions are not bundled yet.** Codes are decoded into P, C, B and U codes, and the JSON of descriptions, whose source has to be permissive and recorded in `assets/dtc/SOURCE.md` (CLAUDE.md 4), comes with the Diagnostics page in phase 5.

## Replay, recordings and the cross-check (phase 2)

- **A replay answers by command, not by the clock.** `ReplayTransport` gives each command the next recorded reply to that same command, in the order recorded, and delivers its pieces at the offsets they had. A recording made by one client at one pace can be played into a client that sends the same commands in another order or at other times, which is what a real car's log needs once the app has changed. A command that is not in the recording gets `?`. An exchange that got no reply, such as a first command a clone lost, stays silent in the replay, so a recording keeps its adapter's misbehaviour. Optionally, the link drops again when it dropped.
- **`tool/record_sim.dart` records the real stack.** The scripted client of phase 1 is gone. An `ObdSession` on a `RecordingTransport` on the simulator makes the traffic, so a recording is what the app really sends. The first replay test of a scripted recording failed because the script never asked which protocol was in use, so the stack, which asks, was not on CAN and sent commands the recording did not have, which is the difference between a stand-in and the real thing. All ten logs now take about 10 seconds and 23 MB, and are still not kept in git.
- **The cross-check against a third-party ELM327 ran, as a separate process.** `tool/crosscheck_emulator.dart` runs an `ObdSession` in real time over TCP against Ircama's ELM327-emulator, which is CC BY-NC-SA 4.0 and cannot be mixed into Apache-2.0 code. It was installed in a throwaway virtual environment outside the repository and started as a process. Nothing of it is in this repository or its history, as code, text or data. The tool has its own small TCP transport, because the app's WiFi transport, with its network guard, is phase 6, and `check_offline.sh` confines sockets under `lib/` to that file. `tool/` is not part of the app.
- **The simulator's multi-frame lines have a space after the colon** (`0: 49 02 ...`) whatever the spaces setting, as the emulator prints them. The datasheet's examples show it with spaces on. The golden fixtures were updated, and the parser reads both this and a last line that is not padded.
- **The simulator's `Elm327Reply` and `Elm327Chunk` became `AdapterOutput` and `AdapterChunk`,** because the client's `Elm327Reply`, which carries the timing and the failure, is the one the rest of the app sees.
- **Deferred on purpose:** trying a batch without the count digit after the adapter refuses one with it (the emulator did), until a real adapter shows a need; reading more than one ECU, for the same reason; and keeping `AdapterMemory` on disk, which belongs to the app's service wiring in phase 3b.

## Testing (phase 2)

- **New components were mutation-checked by hand.** After a component's tests passed, a deliberate bug went in (an off-by-one, a dropped guard, a swapped comparison), and the tests had to fail. At least one test passed for the wrong reason: a fault-code test for a negative response, which would have passed by timing out. It was tightened. This is a habit and not a gate.

## Fonts (phase 3a)

- **Fetched once from a pinned `google/fonts` commit** (`23e54b51ddffbc7713c583748e3bd86f62b1fa4a`), not from each font's own upstream repository, so one commit hash and one set of SHA-256 hashes cover all three families' current release cut. `tool/subset_fonts.sh` re-downloads from that commit and refuses to proceed if a file's hash has changed, so a rebuild is reproducible and a compromised mirror cannot silently swap a font in. This is dev-time only (CLAUDE.md 1); nothing is fetched by the app.
- **Saira's axes are narrowed before subsetting, not after.** `fonttools`' variable-font instancer has to run on the already-subset glyph set, because instancing first leaves the subsetter looking for variation data on glyphs it has already dropped and it errors (`KeyError` on a glyph like `bracketleft.ss02`). `tool/subset_fonts.py` subsets to the character set first, then narrows `wght` to 300-800 and `wdth` to 100-125.
- **The rupee sign comes from Saira in Barlow text too.** Barlow's OFL cut has no ₹ (U+20B9); Saira's does, and it is drawn to match Saira's numerals, which is what money always sits next to. Every Barlow text style lists Saira, and only Saira, as its `fontFamilyFallback`, so a ₹ inside a Barlow label (`₹ THIS TRIP`) renders from Saira and nothing else ever substitutes silently. `test/design/fonts_test.dart` checks the fallback list and that Barlow really has no ₹ of its own, so a future subset that adds one would be caught changing behaviour unexpectedly.
- **No hinting is kept.** Android's text renderer does not run TrueType bytecode, so instructions are dead weight; `fonttools.subset` drops them explicitly rather than relying on subsetting to remove them as a side effect.

## Design system: tokens and theme (phase 3a)

- **`TapePalette` resolves a livery in a mode once**, rather than every component computing "is this Daylight, and does this livery's accent reach 10:1" for itself. DESIGN.md 4.4's Daylight and Night rules (halos off/halved, strokes +50%, `ink.dim`->`ink.mid`, labels to `ink.bright`, an accent under 10:1 giving way to `ink.bright` for numerals while keeping the accent for fills and needles, the rupee sign switching `money.deep`->`money.core`) are specific enough, and touch enough colours, that writing them once and testing that one place against every livery x mode combination (`test/design/theme_test.dart`) was the only way to be sure they were even internally consistent.
- **Contrast is computed, not eyeballed.** `Contrast.ratio` is a standard WCAG relative-luminance calculation; DESIGN.md 11's numbers (7:1 primary, 4.5:1 other text, 10:1 Daylight primary, with `critical` and `stale` exempted from the 7:1/10:1 floor but not the 4.5:1 one) are asserted against every token pair actually used for text, in every livery and mode, rather than checked by looking at a render.
- **The mode controller's window is exactly the thresholds DESIGN.md 4.4 states** (enter Daylight above 5,000 lux, leave below 2,000; enter Night below 20, leave above 60; both need 10 s), with no smoothing beyond that dwell. A shorter or additional filter was considered and dropped: the spec already asks for hysteresis by having different enter and leave thresholds, and stacking a second filter on top would make the transition point unpredictable from the spec's own numbers.

## Motion core (phase 3a)

- **One clock, two implementations, same interface.** `VsyncMotionClock` ticks from a real `Ticker`; `ManualMotionClock` is stepped by hand. Every spring, phosphor bank and smoothed signal takes a `MotionClock` and does not know which it has, which is what lets a widget test drive a spring through an exact sequence of frames and assert on the result, the same way `FakeClock` lets the OBD stack's tests run a drive in no time (CLAUDE.md 5, "Time").
- **A frame is clamped to 50 ms, matching DESIGN.md 5.9 exactly**, and the clamp lives in the clock, not in each spring: a spring given a 3-second dt because the app was backgrounded would otherwise jump straight to its target, which is exactly the "nothing teleports" rule (DESIGN.md 2) being broken by the one component responsible for guaranteeing it never is.
- **`SmoothedSignal` tracks noise as a run of sign flips of the instantaneous rate (two in a row), not a variance or a threshold on the rate's own size.** A steady climb read in whole km/h steps every 100 ms has an instantaneous rate that is not smooth (it is zero for four samples, then a jump), but it never changes sign, so it is not flagged noisy; two flips in a row is specifically the pattern a value oscillating around a true reading produces. A `noiseFloor` (1 unit/s) keeps quantisation of an unmoving value from counting: a signal alternating by 0.5 in its last decimal has a rate under the floor and is never judged by its sign.
- **Lead compensation defaults to zero and is capped at 150 ms, exactly DESIGN.md 5.2's numbers,** because it is explicitly "tuned after the hardware handoff" there — phase 3a has no real adapter latency to tune it against, so the only correct default is off.

## Render primitives (phase 3a)

- **One glyph atlas per (size, weight, density) triple, not per livery.** A sprite is drawn white and tinted at draw time with `BlendMode.modulate`, so ION, EMBER and MONO (all Saira, different weights) share atlases whenever their weight and size happen to match, and a livery switch never rebuilds one. Only the weight (which changes the glyph outlines) and the density (which changes the raster) force a new atlas.
- **A halo atlas is a second, separate atlas built with a nonzero `glowSigmaLp`,** not a blurred copy of the crisp one taken at paint time. `MaskFilter.blur` is baked into the image once when the atlas is built (DESIGN.md 9.3's "never blur at runtime"); Tier 1 asks for this atlas at half resolution (`GlyphAtlasSpec.resolution`), which is a smaller image and a coarser blur, not a smaller draw of the full-resolution one.
- **The grain tile compensates the canvas colour it sits over, not the other way round.** Grain is additive white speckle at a small average opacity; laid directly over the `void`/`carbon.900` gradient, the *result* averages brighter than the token colours by roughly the grain's own opacity. `TapeBackdrop` darkens the gradient's stops by that amount first (`_beneathGrain`, solving `base + grain * (1 - base) = target` for `base`), so the void reads as the void token on average, with grain, rather than the void token before grain is added. DESIGN.md does not say the two combine this way; recorded here since it affects what `void` actually renders as everywhere the backdrop is used.
- **The seven-segment renderer draws all seven segments of a digit as separate sprites, each with its own phosphor level, every frame** — never a "digit changed, cross-fade the whole glyph" tween. This is what makes 1 -> 7 (which shares segments b and c) hold those two segments lit throughout while only a, d, e, f, g move, matching a real VFD and DESIGN.md 6.17's "crossfades segment by segment" literally, not as a metaphor for a glyph-level fade.

## Icon set (phase 3a)

- **Icons are a tiny path DSL (`M`/`L`/`Z`/`O`/`D`/`Q` plus numbers), parsed once into typed ops and cached per enum value**, rather than each icon being a `CustomPainter` or a list of `Offset` literals in Dart. A malformed command is a `FormatException` at first use (caught by `test/design/icons_test.dart`'s "every icon parses" test) rather than a silently-missing line, and the 24-unit-grid and axis-or-45-degree rules (DESIGN.md 4.8) can be checked mechanically against the parsed ops instead of by eye.

One second means the 90th-percentile judgement is never more than a second stale.

## Fuel, money and trips (phase 4)

- **A closed throttle is where the car reads it at idle, not 0.** PID 11 is the absolute throttle position, which reads 10 to 20% with the throttle shut (the simulator's reads 12%). CLAUDE.md 8.4's "throttle at 0" therefore never matched, and air-based estimates counted a coast with the fuel cut as burning: +5.7% on the sporty manual in city driving. `FuelEstimator` now learns the closed reading (the lowest throttle seen while idling) and judges the cut from it, falling back to 2% until the car has idled. After the fix every petrol profile is within about 2% of the truth on every scenario.
- **Speed-density uses an rpm-shaped VE, not a flat 0.85.** A flat 0.85 over-counts fuel at idle by ~20% (the simulator's VE is 0.70 at idle, 0.85 at 2000 rpm), which put idle cost 17% high on a jam. `FuelConstants.volumetricEfficiencyShape` is a generic naturally-aspirated shape, 1.0 at 2000 rpm; the level is still 0.85 and is what calibration corrects. **Caveat:** the simulator's curve and this shape are both "a typical road engine", so agreement in tests proves the machinery, not accuracy on a real car; real cars are expected to need the calibration factor. Pass an empty shape for a flat VE.
- **Air-based estimates during a suspected fuel cut are 0**, not the reported air converted to fuel (air still flows in a cut). 5E is never overridden.
- **A gap in the estimates over 30 s is not integrated at all; a gap over 3 s is filled with the average of its two sides and flagged.** Burning nothing is a smaller error than making fuel up, and a reconnect never brings a spike.
- **Rupee blocks go to the bucket with the most spend not yet in a block,** not to the bucket of the sample that crossed the whole rupee. The latter favoured whichever bucket was burning at the crossing (1.8 blocks off on a jam trip); this keeps each bucket within one block of its cost.
- **Hard-acceleration fuel waits, in order, for the detector.** A hard acceleration is only known after 1 s (or 2 s of throttle), so the fuel from those first moments is held and put in the hard bucket if the event confirms, or in normal driving if it does not.
- **The fill-up ledger counts the raw estimate** (before calibration), since the correction is what is being worked out; a factor from a fill-up needs at least 1 L on each side and a ratio between 0.4 and 2.5 (further out means the app missed trips, and is not used).
- **The engine is judged off from the connection status, not the last voltage:** the car stops answering (waiting for ignition), or answers with rpm 0 and under 13 V. A lost adapter link says nothing about the engine, so the trip carries on (and ends after 5 minutes of nothing).
- **The fuel PID moves to the fast tier while a trip is recorded** (`RecordingDemand`): 5E, MAF or MAP, whichever is the source, or all three until one is chosen.

## Real transports and the connect path (phase 6)

- **BLE is a thin Kotlin channel, not `flutter_blue_plus` or `flutter_reactive_ble`.** CLAUDE.md 5 says to verify the licence first and to ask if unsure, and offers a thin channel as an alternative. A channel needs no dependency, no licence check, no transitive dependency and no Play Services risk, and BLE ELM327s need only scan, connect, subscribe and write. The cost is that the GATT logic (which characteristics carry the serial data) is ours and unverified; the handoff checks it first, and a failed lookup says so in words.
- **One Dart transport for both radios.** `NativeLink` (open, close, send, incoming, lost) is the whole of what the OBD layer knows of a radio; `NativeLinkTransport` gives the states, the failures and the cancel-a-connect rule once. `AdapterRadio` speaks one channel vocabulary for both Kotlin channels, and each channel is named `tapedash/<bt_classic|ble>`.
- **The network guard refuses host names, not only public addresses.** A name is looked up, and a look-up is itself a request to the network, so `localhost` and `obd.local` are refused; a WiFi adapter is entered as an address, and `127.0.0.1` (for the simulator over `adb reverse`) and `10.0.2.2` are literal addresses that pass. IPv4-mapped IPv6 addresses take the IPv4 rule.
- **Bluetooth Classic tries three sockets.** Cheap clones are fussy: the secure SPP socket, the insecure one, then RFCOMM channel 1 by reflection. This is a widely used workaround and is unverified here.
- **Permissions:** `BLUETOOTH_CONNECT` and `BLUETOOTH_SCAN` (declared `neverForLocation`) on Android 12+, asked for at run time by one helper shared by both channels; before Android 12 the old `BLUETOOTH` and `BLUETOOTH_ADMIN` are install-time, and scanning uses the location permission the GPS already needs. `INTERNET` is declared for the WiFi socket and is on CLAUDE.md 4's list.
- **The connect flow saves nothing as the adapter until its last step**, but keeps the car's setup and the price as they are entered, so going back never loses them.
- **The app chooses its drive from `AdapterStore`:** an adapter chosen and in use is a `LiveDrive` and the demo is not built; otherwise the demo runs. Switching rebuilds the drive screen (a different drive is a different shell). The demo keeps its own money and its own simulated GPS; a real drive uses the real money and the phone's GPS. Compatibility mode and recording apply the next time the drive is made, which Garage does at once (parked only).
- **Recording is opt-in and per drive:** one file for each drive, named `session-<date>-<time>-<kind>.log`, written every 20 s and atomically (a temporary name, then a rename) so that a phone that dies leaves the last good copy. It is in the app's external files folder, reachable over USB with `adb pull` and needing no storage permission.
- **`DisplayController` is the one place the phone meets the design system's display pieces.** Night's brightness uses the design system's own lux curve and floor; the phone's own brightness is left alone in the normal mode; Daylight is 1.0; a phone above 50 C is capped at 0.5 whatever the mode. The frame-rate cap is applied to the motion clock by a small binder widget. Every call to the phone may fail without stopping the app.
- **Two floors for Night's brightness appear in DESIGN.md (12% in 4.4 and 20% in 8);** the app uses 12% everywhere and the HUD's 20% is left to the HUD.

## First real drive (2026-09-30)

The first drive on a real phone (a 120 Hz flagship, a release build) and a real BLE adapter (`OBDBLE`), from two screenshots and the human's account. Connected over BLE, fuel from MAF, **poll rate 1.3 cycles a second**, 121 fps at tier FULL.

- **(Superseded on 2026-09-30, see "The tach was a pendulum" below: the tracking filter was removed.) A slow adapter is accepted, and smoothed in software.** 1.3 a second is what a cheap BLE ELM327 gives (against the simulator's Bluetooth clone at about 9); the human's call is to accept it rather than chase the rate. The answer is a tracking filter (a constant-velocity Kalman filter, `lib/core/dsp/`) between the samples and the spring, described in DESIGN.md 5.2. **DESIGN.md 5.2 was amended for it**, at the human's request: the spring is no longer restarted per sample for RPM, speed, throttle and load, but stepped in closed form towards the filter's estimate every frame.
- **Why a Kalman filter, not a moving average or a longer spring.** An average or a slower spring only adds delay, and the delay is the problem (a sample already 0.3 s old on arrival, and up to 1 s to the next). The filter carries velocity, so it can move on between samples and make up the latency, and its gain comes from two numbers with a physical meaning (how noisy a sample is, how hard the signal can be pushed) rather than a smoothing constant to be tuned by eye.
- **The extrapolation is bounded three ways,** because it is a guess: a time constant (the run ahead tends to `velocity * tau`, never more), a cap in the signal's own unit, and the signal's physical range; and it is scaled down by how far the velocity is trusted. The price is that a lone jump (no follow-up sample) overshoots by up to the cap until the next sample; a lift after a rev pull does the same. That is inherent to running ahead of the data, and is why the caps are small.
- **What it buys, measured against a made-up truth** (samples 0.77 s +/- 0.25 s apart, 0.3 s late, rounded like the PIDs; `test/design/tracking_test.dart`): tach RMS error 740 rpm with the old spring, 540 with the tracker; speedometer 4.8 km/h, 3.1. The tach's number is dominated by a floor (1.3 samples a second cannot resolve a 3 s wobble in the revs), and the sweep of the tuning (`sigmaA`, tau, cap) moved it by under 50 rpm either way. **These are simulator numbers; the tuning is a guess to be checked on a real recording.**
- **Stale limit adapts to the signal's rhythm** (2.5 times its usual gap, at most 4 s), so a slow adapter's ordinary jitter does not flash a value to the stale colour.
- **The ECU is "silent" only after three misses and four seconds without an answer** (`PollConfig.silentFor`). Three misses in a row were 2 s at 1.3 a second, and a silent ECU means "the ignition went off", which ends a trip after ten more seconds and brings up the Debrief and the Review page. The human drove one continuous trip, stopping at a signal with the engine running, and saw a trip of 8 min, 1.3 km and a second one of 1:49 and 0.4 km within two minutes. **The cause was not established** (no logs were read); this is the likeliest path from the code, and it is a hypothesis until a recording shows it.
- **A test's window was moved, not its tolerance:** `connection_test`'s "the values after it are the car's again" compares the first 200 readings after the ignition returns to the truth within 350 rpm; the later moment at which the ECU is now called silent shifted which readings landed in the cranking and put one (205 against 555) 0.6 rpm past it. It now skips the first three seconds after the ignition, the cranking, where the rpm climbs faster than a sample can say. Worth a second look if the human prefers the window kept.

## Ethanol in the petrol, the breakdown's rounding, the dock, and idle time (2026-09-30)

Follow-ups to the first real drive, done before the second one.

- **E20 changes the fuel figure by 7.5%, so the app has a petrol blend** (`PetrolBlend`, `lib/core/fuel_blend.dart`). The MAF and speed-density methods turn a mass of air into litres of fuel with an air-fuel ratio and a density. Ethanol needs less air per kilo (9.0 to 1 against 14.7) and is denser (789 g/L against 740), and a car that holds a stoichiometric mixture (the oxygen sensor does, at idle and in steady driving) burns more litres for the same air: **E10 about 3.6%, E20 about 7.5%** (AFR 13.50 and 749.8 g/L for E20; the mass-weighted sum of what each fuel needs, not the volume-weighted). Read as E0, an E20 car's estimate is 7% low until a fill-up calibrates it. The simulator's ground truth follows the blend too (`VehicleProfile.withBlend`), so the correction is tested against a car that really burns it: told, E20 is inside the CLAUDE.md 10 tolerances; not told, it reads 4 to 11% low; and two full tanks put right the one that was not told.
- **Defaults.** `VehicleSetup` itself defaults to E0 (the constants of CLAUDE.md 8.4, and what every simulator profile burns); **a new install starts with E20** (`VehicleSetup.indiaDefault`), and so does a setup saved before the setting existed, since that is what the pumps in India sell now. Garage and the connect flow have the choice: E0, E10, E20.
- **What the blend does not do.** PID 5E is left alone: it is the ECU's own figure, and whether an ECU computes it from the injected volume (right for any blend) or from air and a fixed 14.7 (7% low on E20) is not known; calibration takes care of the second. Fuel that is a mix of E10 and E20 from two pumps is between the two, and old fuel in the tank lags the setting: the blend is an estimate to within a couple of percent, and calibration is what closes the rest. **A cold start and full throttle run rich whatever the fuel**, and neither is modelled. The blend's lower energy (E20 is about 8% less per gram) is why the km/L falls on E20; that needs no correction, because the litres are the litres.
- **The where-it-went figures are apportioned** (`apportion`, largest remainder), so the rupees and the percents on Review and Money are whole numbers that add up to their own total, moving no part by more than one from its own rounding. Live, a part can move by one as the fractions change.
- **The dock keeps the pages' left margin** (the right is left open: the four buttons need most of the width of a 640 lp screen).
- **Idle time counts half of a mixed interval.** It counted only intervals with the car standing at both ends, which loses up to one sample interval at each end of every stop: 6.8% of the idle time in `aggressive_city` behind an adapter giving 1.3 cycles a second. The halves cancel. `AdapterQuirks.slowBle` models that adapter, and the accuracy criteria of CLAUDE.md 10 (distance, fuel, idle time, idle cost) are tested behind it.
- **The idle cost of the first drive is not shown to be wrong.** ₹4 for "1 min" at ₹115 a litre (the price entered) is between 1.4 and 4 L/h depending on how the minute rounds, against 0.6 to 1 L/h for a warm 1.5 L engine. A cold start idles fast (about 1200 rpm, on a rich mixture): the trip was the first of the morning, and 1.5 L/h is what MAF would say for it. Nothing in the attribution was found wrong, and the pipeline is inside 7% of the simulator's idle fuel at any adapter speed. Whether the MAF sensor reads high at idle on this car needs the recording (vitals lines carry `maf`, `lph`, `idle_s`, `idle_l`).
- **A recording carries the app's own notes** (`@` lines in the session log; replay ignores them): the setup, the connection status, the engine, the mode, the trip phase, and every 5 s the numbers the money is made of. The first real drive could not say why a trip ended, because a log held only the traffic. **A debug or profile build records its drives until Garage says not to** (a release build does not); a choice made in Garage wins either way.

## The tach was a pendulum (2026-09-30)

Two long drives on the debug build (72 and 62 minutes, 15.8 and 14.5 km, the same `OBDBLE` adapter) left recordings, and the human's verdict on the tach was "a bit pendulum-like". **The tracking filter of the day before was the cause, and my claim for it was wrong.**

- **What the recordings say about the data:** 5,475 RPM samples in 4,334 s: one every 0.79 s (median 0.75, 90th percentile 0.93, worst 2.05 s), each request a round trip of about 140 ms; between two samples the rpm differs by 64 rpm at the median and by 380 to 460 at the 90th percentile (a CVT and stop-go traffic).
- **What the tracker did with it:** replayed through the real `SmoothedSignal` against the straight line through the samples, the plain spring had 159 rpm RMS error, the tracker 354; the tracker's display went outside the two neighbouring samples in 62% of frames (the spring in 17%) and reversed direction 57 times a minute against the 25 the data itself does. Extrapolating the velocity of samples that jump like that is wrong more often than right: every gear change and throttle blip was overshot and then pulled back. The earlier test measured 740 against 540 rpm because its truth was a smooth sine wave; that says nothing about a real car. **A synthetic truth cannot judge a smoothing filter; the fixture of a real drive can, and now does** (`test/design/real_drive_smoothing_test.dart`, from `test/design/fixtures/real_ble_drive.json`).
- **The plain spring was not fine either:** on the same drive the needle stood almost still for 57 to 62% of the time the revs were moving (a stair: move, stop, move, stop).
- **The fix is a playout buffer, not a predictor** (`lib/core/dsp/playout.dart`, DESIGN.md 5.2): show the straight line between the two samples either side of a moment 0.65 of a sample gap in the past. It cannot overshoot, because it never leaves the interval between two readings, and it does not stand still, because it is always between two. The price is delay: about half a second at this adapter, scaled to the gap, so a fast adapter is not held back. Measured on the busiest 300 s of the first drive: the needle stands still 16% of the time (from 57%), its jerk falls from 11,800 to 5,800 rpm/s^2, it reverses as often as the plain spring (36.6 a minute, the data's own 30.2), and its RMS error against the data rises 8% (221 to 239 rpm), which is the delay. The speedometer's number stands still 14% of the time (from 63%) and its jerk falls fourfold.
- **The sweep that chose the numbers** (the first drive, 900 s): delay 0.35, 0.5, 0.6 and 0.8 s gave standing 48, 34, 26 and 19% and RMS 155, 162, 170 and 191 rpm (a hold at the newest sample), so the smoothness is bought with delay and half a second was the middle; a tail that carries the last slope on, fading, took standing from 34 to 18% for three reversals a minute more; a softer spring (200 instead of 380, critically damped) cut the jerk by a third for 5 rpm more error, and was **not taken**: the needle spring stays the design's token. **If the needle still feels jerky, the next step is a softer spring for the tach, or a longer delay** (`TapePlayout`, `PlayoutSpec.delayShare`); both are numbers.
- **Not tried, and the reason: a faster poll.** The log shows why the rate is 1.3 a second: the poller sends a batch of five PIDs, gets back two ECUs' interleaved multi-frame replies (both are longer than the 7 bytes of one CAN frame, and one of them has no MAF), cannot sort them into one set of readings, and falls back to one PID a request, 140 ms each, for 60 s at a time (28 batch attempts and 5,400 single requests in the first drive). Requests small enough to be one frame each (two or three PIDs) would be answered as plain lines by both ECUs, but the ELM's "one response" digit could then return after the ECU that lacks a PID answers, so it needs each PID's ECUs learnt from the discovery replies first (the two bitmaps of `0100` are in the log: one ECU has no 10 or 13...). Estimated gain: RPM from 1.3 to about 2.2 samples a second. Not done: it changes what the app asks a real car, and the smoothing is what was asked for.
- **The idle cost is real.** Idle fuel over the two drives comes to 1.27 and 1.31 L/h (0.407 L in 1,155 s, 0.232 L in 639 s) at MAF 2.4 to 3.3 g/s and 750 to 790 rpm on E20, consistent with each other and with the MAF the car reports.
- **The average km/L is in the floor** of the Apex cluster, right after the trip km (`TripFloor`), a dash until the trip has some distance, and absent for a car that gives no fuel figure. The other clusters show no trip distance, so nothing was added to them.

## End trip, telemetry history, channels in Review, and the map (2026-09-30)

- **A trip ended by hand stays ended while the car stands.** `endNow` used to let the next voltage reading start a new trip within seconds if the engine was running. With the engine on, `_endedByHand` holds the recorder in `none` until the car moves (`vehicle.mode`) or the engine has gone off. The alternative, a new trip at once, would put the Debrief's trip and a fresh empty one side by side at the destination.
- **No confirmation on End trip.** DESIGN.md keeps slide-to-confirm for what cannot be undone (codes, all data); a trip is kept, only closed, and the button is in the parked dock, which is out of reach while moving. If it turns out to be pressed by accident, a confirm is the next step.
- **Five dock buttons, so a dense button and scale-to-fit** (below 900 lp), in preference to two rows (the parked layouts reserve one row's height, 0.20 H, for the dock) or dropping a button. The last resort, `FittedBox`, keeps it inside the margins on any width; the cost is buttons about 52 lp tall at 640, still over the 48 lp touch target.
- **The telemetry history is the drive's, not the tile's** (`SignalHistory` on `DriveSignals`): a minute at 2 Hz, in memory, sampled on the scheduler so it does not depend on a screen being mounted. It was not made persistent: the trip's own samples (now with load, coolant and voltage) are the record that lasts, and a minute of history is for the tile.
- **Three channels, not all of them:** load, coolant and voltage are what the Telemetry tiles show that a trip did not keep (rpm, speed and throttle already were). MAF, intake air and manifold pressure are not recorded per sample; the trip's fuel figures come from them already. Older trips read as null, and the selector offers only what the trip has.
- **The scrolling selector rather than a second row or shorter labels:** the route panel is 115 lp tall at 360 lp and cannot spare a row, and "THROTTLE" at 14 lp is 70 lp wide.
- **The route view is a scale and an offset applied when drawing**, not a redrawn geometry: the geometry stays as fitted, and line widths are divided by the scale so they keep their look. The cost is the thinning (1,000 points for the trip); the fix, if a deep zoom looks poor, is to thin to what is visible (a level of detail), not to raise the cap.
- **A touch on the map skips the Debrief at the touch** (a `Listener`), because once the map has a double-tap gesture a tap is only recognised after the double-tap wait of about 300 ms.

## A trip to replay, and an engine to hear (2026-09-30)

- **The replay is a mode of Review, not a screen.** The instruments take the receipt's place (the right 38%) and the route panel stays where it is, so nothing is rebuilt when it starts and a touch still skips the Debrief. The tip gives its room to the map for the replay; the alternative, a full-screen player, would have had to hide the parked dock, which the shell owns.
- **The car is placed by the odometer, not the time.** A stopped car's scattered fixes are dropped from the route (they are within a metre), so a place by time would creep through a stop. Between two route points the car's share is the distance the trip's odometer says it covered; where the odometer did not move at all (wandering GPS) it goes by time so that it never jumps.
- **The replay's totals are scaled to the trip's own.** The integrals of the one-second samples differ from the trip's live totals by about a percent, and a replay that ended on another ₹ than the receipt's would be a figure that does not add up (CLAUDE.md 1.6).
- **Readouts rest on whole digits** (`PlaybackChannel.step`): a number that moves every frame is part-way through an odometer roll nearly all of the time. A replay's numbers are set like a parked screen's (DESIGN.md 5.6).
- **Chase camera: position exact, zoom and turn sprung.** An exact position keeps the car from drifting on the screen; the turn and the zoom follow on slow critically damped springs, so a corner or a change of speed is felt and not jolted. The zoom shows 45 s of travel across the panel (at least 260 m): with no basemap, a closer view shows only a line, and a wider one shows the road's shape. A pinch moves a bias, not the zoom, so that the camera keeps choosing. A drag lets go of the car (as any map does); FOLLOW takes it back.
- **A grid and a road, because there is no map.** A dark ribbon under the line and a faint grid every 25 m to 5 km (the nearest at least 44 lp apart) are what the ground is, until there is a basemap. They are cheap: one more pass of the route, and at most about thirty lines.
- **The engine is synthesised, not sampled.** No recording to license (CC0 only would have been safe; CC-BY needs credit, CC-BY-SA spreads, NC is out for F-Droid), nothing added to the APK, every parameter tunable by ear in one place, and it follows the revs continuously where a looped sample would be pitch-shifted and cross-faded. The price: it is a model, and it can sound like one.
- **No audio library.** Oboe and SoLoud would add an NDK build for a few lines of arithmetic; `AudioTrack` through a thin channel is the platform's own API (CLAUDE.md 5: prefer about 100 lines of our own code). The synth is pure Dart so that it is tested headlessly and rendered to WAV by a tool; it runs in an isolate so that the drive's frames never wait for audio.
- **32 kHz, mono, 16-bit.** The content is under a few kHz; the platform resamples; a block of it costs a fraction of a percent of a core.
- **Car audio only by default, no service, no focus.** A phone that blares an engine from the dash when the Bluetooth link drops is the failure that matters, so it does not start without car audio, stops on ACTION_AUDIO_BECOMING_NOISY, and checks the outputs about once a second. It asks for no audio focus (music carries on under it) and stops with the screen, so no foreground service and no new permission (CLAUDE.md 4). The Garage test and a replay play on any output, because they are asked for, parked.
- **Passive by rule.** The engine sound carries only what the tach carries (DESIGN.md 5.10); a beep, a voice or a cue would be coaching by another sense, which CLAUDE.md 1.5 forbids while driving.
- **Not the map.** OpenStreetMap under the route was assessed and deferred: flutter_map depends on `http` (banned by the offline check), OSM's tile servers forbid offline use and prefetching, the data must be a file the user supplies (Protomaps builds, or tilemaker on a Geofabrik extract), the credit "© OpenStreetMap contributors" must show on the map, and nothing is to be bundled (distributing an extract is distributing an ODbL database). It is a reader and a renderer of our own and a file picker; a later session.


## Survey drive (2026-10-16)

The first real recordings showed two ECUs answering with different PID sets, 9 of 32 PIDs read, and 1.3 reads a second. The human asked for a survey mode so the next pages (an electrical one, an engine one) can be designed from what the car gives. See `docs/SURVEY.md`.

- **A survey takes the adapter over; it does not ride on the dashboard's poller.** The poller reads 11 PIDs it has formulas for, one command at a time, with headers off. A survey needs headers on, raw replies for PIDs nobody has decoded, and a request mix of its own; sharing the poller would have meant changing its contract for a one-off. So `LiveDrive` is disposed (its link closed) before `SurveyDrive` opens the adapter, and made again when the survey screen is left. The cost: no dashboard on the survey drive. The `SurveyRunner` is built on the same `Elm327Client` and `Elm327Initializer` as the dashboard, so the clone tolerance is shared.
- **Read-only, no VIN, by construction and by test.** The runner sends Mode 01, 03, 06, 07, 09 (PIDs 00, 04, 06, 0A) and 0A, and a short list of AT commands. `survey_test.dart` fails on any other command, on Mode 04, and on 09 02. The VIN is personal and a public repo holds the recordings.
- **Headers on to find the ECUs, a receive filter to read them, headers off for the drive.** With both ECUs answering, the real adapter completes only one multi-frame answer (the recordings show first frames from both and continuation lines for one), so a batch of PIDs lost half its data and the dashboard fell back to one PID a request. `ATCRA <id>` makes the adapter listen to one ECU, which then completes. Headers are on only while the ECUs are being told apart; the drive loop is headers off, which is the format the code has been proven on, and the filter says whose answer it is. **All of it unverified on the real adapter**: each has a way back (`SurveyFilter.refused`, a batch of one, no headers) and the log says which was used.
- **A filter that lets nothing through is detected and dropped.** If the ID parsed from the headers is not the ID the adapter filters on, every request after `ATCRA` would be `NO DATA` and the survey would take the car for switched off. Three failed requests after setting a filter that has not yet let anything through, or a probe request that does not come back from the ECU it asked for, make it give the filter up. Found by reading the design critically, not by the simulator; the simulator got a quirk (`deadReceiveFilter`) to test it.
- **The scheduler reads whatever is most overdue, and leaves an ECU only when it must.** A request for six PIDs costs 172 ms against 141 ms for one (measured in the recordings), so every request is filled. Each PID has a period by tier (core 0.4 s, sensors 2 s, temperatures 10 s, status 60 s) and the PIDs are picked by how many times over their period they are. A switch of ECU is two commands, as long as a request each; the first version switched about once a second for one PID of the small ECU and spent a quarter of the time doing it (89 switches in 50 s, revs at 1.4 Hz). It now stays unless the other ECU is twice overdue or there is nothing left to gain where it is: 21 switches, revs at 2.3 Hz in the simulator. The numbers are the simulator's, behind an adapter given the measured timing.
- **`measured_ble` replaces a wrong guess.** The `slow_ble` quirks preset says the adapter takes no batches. The recordings contain 217 batches of 4 to 6 PIDs that were answered, at 172 ms. The preset is left alone (tests use it) and a new one has the measured figures. The dashboard's polling around that assumption is not touched here, but it is the reason for the 1.3 Hz: every PID is one request because the batch's second ECU is cut off. With `ATCRA` the dashboard could do the same.
- **No Mode 22 / UDS probing.** Standard OBD has no battery current or alternator data; Honda keeps those, if the car has them, in manufacturer services. A search found no list for this car (only a Torque Pro list for other models). A scan of the identifier space is hours at 140 ms a request and sends requests the maker has not published to a car's computers. Not done; if the survey points at it, it is a separate decision with the human.
- **The survey is guided, and the guide writes the marks.** OBD gives one electrical number, the module voltage, so what each load does has to be observed. The first version had the human tap what they switched; the human asked for a guided survey, and tapping while remembering an order is the part most likely to go wrong. `SurveyGuide` (pure, on the injected scheduler) leads sixteen parked steps (headlights, blower low and high, A/C, defogger, wipers, steering, an optional rev), each with a countdown, and writes `survey mark id=... state=on|off pass=N` as the step it names begins. The log has what the app *asked for* and when, not what was done; the human says what they could not do. Two runs: before the drive and after (warm). A skipped step moves on; stopping a run writes off whatever it had said was on, so the log never ends a run with a load on.
- **The guide only speaks while the car stands, and stops the moment it moves** (CLAUDE.md 1.5: nothing asked of the driver, no prompts while driving). It begins only when the survey is reading the car and the car has stood still for five seconds; it holds (the clock stops) if the car stops answering; the driving screen has no part in it and shows nothing to touch. The repeat is offered at once only if the first run was skipped or stopped; after a full run it waits until there has been a drive of 15 minutes.
- **The optional rev is a step the person can skip, and says so.** A few seconds to about 2,000 rpm in P with the handbrake on is ordinary; it is there because it shows what the engine reports with no road load, for the engine page. It is not required and not above 2,000.
- **The survey screen rebuilds once a second.** DESIGN.md 9.3 says live data never rebuilds a widget; that is for driving screens, which draw at 60 fps. This screen is a column of text and shows nothing that moves, so a once-a-second rebuild is the simplest correct thing. It uses only tokens and the existing components, and passes the design lint.
- **`SurveyDrive` does not wait for the recorder to tidy its streams.** Awaiting `RecordingTransport.dispose()` stalls under the widget tester's fake-async zone (it completes in a real one, as the plain unit test shows). Nothing depends on it: what must be closed before the dashboard opens the adapter again is the link, and that is awaited.
- **The simulated twin-ECU car is built from the first recordings' two PID sets** (`petrol_cvt_twin_ecu`, protocol 7, ECUs at `18DAF110` and `18DAF111`). The ECU addresses are made up; the PID sets are the car's. The values behind the PIDs the app does not read are invented from the car's state, with the right lengths, and are for exercising the survey, not for anything about the engine. The profile is not in `VehicleProfiles.all`, so no scenario test runs it by accident.


## Insights (2026-10-18)

Nine ideas from the pitch, built on what the trips already store: Current, Powerflow, Power curve, Gearbox, Toll Map, Tank count, Cold-start bill, Ghost commute and Year on Tape, with a Share button on the last.

- **A new pure directory, `lib/insights/`.** The analyses read finished trips and their one-second samples and return plain values, so they are tested headlessly like `coach/`. It is on the architecture test's pure list and in CLAUDE.md's tree.
- **One parked-only destination, not seven new pages.** The Strip is five pages and moving between them is the cockpit's grammar (DESIGN.md 7.1). The insights open from the parked dock as one full-screen form (like Diagnostics) with a scrolling selector, and close when the car moves. The tank count is the exception: it fills the Money page's existing fuel-left slot.
- **Wheel power is a model, labelled one.** The car sends no torque. Wheel power is the force to accelerate (1250 kg), roll (Crr 0.012) and push air (CdA 0.65) times speed, with acceleration over a 3 s window because OBD speed is whole km/h. No grade. The constants are in `InsightConstants`, in one place. The energy in a litre is petrol 32 MJ and ethanol 21.1 MJ mixed by volume (E20 is 8.28 kWh/L). The wheel share is capped at 40% so a bad model cannot show an engine better than physics.
- **A dip is a dent, never a named load.** The City reports no battery current. A dip is a drop of 0.35 V under the steady voltage that recovers to within 0.15 V in 2 to 60 s. What caused it is not claimed; the survey drive's marks are what can name them. A voltage that steps down and stays is the regulator, not a dip.
- **Resting voltage is its own log.** A trip starts when the engine does, so its samples never hold the battery at rest. `RestVoltageWatcher` takes one settled reading (within 0.06 V for 8 s, between 11 and 13 V, the engine off with the ignition on) at most every 6 hours into a `shared_preferences` list of 120.
- **Gears are crowds.** A gear is a ratio bin that stands 3 times above the usual bin and above the bins a few away; fewer than two such crowds, or under 55% of moments near them, is a fan (a CVT) and no gear is claimed.
- **The tank is counted, not sensed.** The City sends no fuel level. Litres left are the tank as of the last full fill-up, less the app's estimate since (with the calibration), plus part-fills since, clamped to the tank. Null until a full tank is logged. It rides the existing remaining-fuel slot of `TripComputer`, and the screens mark it "≈".
- **Toll spots are places, not roads.** Stops of 15 s or more with the engine on (speed under 2 km/h) are grouped within 150 m (the two sides of a junction are about 100 m apart); places under 40 s in all are dropped; the 12 dearest are drawn. The map is plain equirectangular, north up, as the route trail is.
- **The cold-start bill is against the car's own warm cost.** Warm is a coolant of 80 °C or more; the baseline is the median ₹/km of at least 3 minutes of warm driving; the extra is the cold windows' spend over that baseline, moving windows only. A trip that did not start under 65 °C, or has no warm stretch, has none.
- **Ghost commute compares rupees, never minutes.** Same route means both ends within 400 m, a length within 1.3 times, and 24 points along the route within 180 m on average. The page never says "faster".
- **Share is the system share sheet, with a picture the app made.** The poster is drawn by the app, written to its cache, and handed to Android's share chooser through a `FileProvider`. No network code and no permission; what the person picks in the sheet is their choice. androidx.core (Apache-2.0) is already in the app through the Flutter embedding.
- **The first real drives broke the first wheel-power model, twice.** Run against `recordings/real` (the City's five-second vitals), the made-up-drive version gave 100 kW at 2,157 rpm: a real speed jump (46 then 95 km/h on a 40 km/h road) read as a pull, and noise in whole-km/h speed, counted only when it pulls, made the engine look as if it did work. Now: a median of three takes one-reading spikes out, the acceleration is the slope of a line through the speeds within 3 s either side, and a moment that asks more than 5 m/s2 is dropped. "Highest seen" is the peak of the 95th-percentile edge, not the highest dot. The real City's gearbox comes out as a fan (it is a CVT), its edge peaks at about 30 kW at 3,100 rpm and its wheel share of the fuel at 7 to 17%. `test/unit/insights/real_drives_test.dart` keeps those checks.
- **A gear is told from a CVT's cruise by what happens while the speed changes.** A CVT cruising at a few steady speeds makes crowds of ratios that look like gears; but it lets the ratio fall as the speed rises, where a gearbox holds it. Moments with the speed changing by 2 km/h in 2 s must sit at the gears' ratios (at least half of them) or the car is called a fan.
- **Gears are not numbered.** A first gear never driven in does not show, so counting from the shortest found could label second as first. They are labelled with their ratio.



## Demo Mode removed, a GPS-only source, and a steadier Bluetooth (2026-10-23)

The human's instruction, after the connection problem on the first real adapters persisted: *remove demo mode (some fallbacks still went to it), add another mode that shows speed with just GPS, add more stability with Bluetooth (the adapter shows as both `OBDBLE` and `OBDII`), and give a clean APK without demo mode; remove this and log this.*

**Demo Mode is gone from the app.**
- **Why it had to go, not just be hidden:** the app chose "the adapter if one was chosen *and* in use, else the demo". Any state that failed that test (the old "Drive from this adapter" switch in Garage, a forgotten adapter, a launch before the settings loaded) quietly showed a simulated car with real-looking numbers. A drive screen that can be a simulation without saying so is the wrong thing to have in a car, so the fix is that the app has no simulation to fall back to.
- **What was removed:** `DemoDrive`, `DemoLocationSource`, `DemoControl`, the demo settings and Garage group, `AppServices.demo` and its separate in-memory money, the DEMO badge (`StatusStripRight.demoMode`, `DriveSignals.demoMode`), `DriveFeed.isDemo`, the `TapeIcon.demo` icon, the onboarding "Try a demo drive" and the `TapeDashApp.onboarding`/`scenario` parameters. CLAUDE.md 7 and 7.6, DESIGN.md 6.9, 7.8, 7.11, 7.12 and the README were changed to match.
- **What stays:** the simulator (`lib/sim/`), the Design Lab, `tool/sim_server.dart` and every test that runs the whole app on a simulated car. The widget tests now do it through the production path: `test/support/sim_shell.dart` gives a chosen adapter whose transport is `SimTransport` (`SimRig`), and `SimDriveShell` for the screens that are built directly (the old `DemoDrive` lives on as `SimDrive` in `test/support/`, not in `lib/`). `integration_test/` reaches the simulator over WiFi (`integration_test/sim_connect.dart`).
- **Old simulated trips** (`is_demo = 1` in a phone's database) are **not deleted**: the column stays, and the trip library, the statistics and the insights never list or count them. Nothing makes one now. "Delete all data" in Garage still removes them. Deleting a person's rows on an upgrade, even simulated ones, is not something to do without asking.
- **The source is a setting that is asked for and never guessed:** `AdapterStore.source` is `obd`, `gps` or none. None (a fresh install, or after forgetting the adapter) shows the cold open's choice again, without replaying the cold open. An adapter that has been chosen is the source whatever the old demo switch said (`adapter_use_live` is no longer read). An adapter that will not connect stays "looking for your adapter" and retries; nothing replaces it.

**GPS only** (`lib/location/gps_drive.dart`, `lib/app/gps_shell.dart`, `lib/ui/pages/drive/gps_cluster.dart`, DESIGN.md 7.15).
- **One screen, not the strip.** The strip's other pages (Money, Review, Coach, History) and four of five clusters have nothing to read without a car, and drawing empty places for them would be the same dishonesty as a demo. The screen is the Minimal cluster's layout with the trip figures a GPS can honestly give.
- **It rides on `VehicleState`** (speed only), so the smoothing, the Motion/Parked rules, the HUD and the look are the ones that already work. The HUD gets a `layout` override and a `showRpm` switch so it can show the speed alone.
- **The speed is the receiver's Doppler speed**, taken as zero below 1.5 km/h (a receiver at rest reports a metre a second of drift). The distance is that speed over time (trapezoid, gaps over 5 s not driven over), never the sum of positions, which grow at a red light. A fix worse than 100 m is not used; the "fastest" only counts a fix better than 30 m. Tested against the simulator's ground truth (a 12-minute city drive: distance within 3%).
- **No trips, no fuel, no money, no coach, no engine sound** in this mode. A GPS trip log is possible later; it was not asked for and the Trip model is built around the engine.
- **Garage → Speed from** switches between the car's adapter and the GPS, keeping the adapter. Choosing the adapter with none set opens the connect flow and changes nothing until it finishes.

**Bluetooth: what was changed and why** (all native parts **unverified on a phone**, see STATUS.md).
- **One Bluetooth choice that finds both radios.** Many adapters answer on Classic as `OBDII` and on Low Energy as `OBDBLE` at once, and nobody should have to know which is which. The connect flow's search runs both, lists each adapter with its radio and how close it is (the RSSI, as Close / Near / Far, nearest first: the adapter in your own car is the one beside you, and a neighbour's is far), and **tries a Low Energy adapter before taking it, as it already did a Classic one**. When the pick will not open and the other radio has something that looks like an adapter, "Try OBDBLE" is offered.
- **No automatic switching between radios while driving.** A failover that quietly moves from one radio to the other is the same kind of guess as the demo fallback, and a dual-mode adapter that refuses a second connection can make it flap. The person chooses; the log says what happened.
- **BLE (`BleChannel.kt`):** the link is let go of properly (`disconnect()`, wait for the stack's callback, only then `close()`, a short settle) before the next is made, because closing at once can leave the adapter holding a connection nobody owns, which is one explanation for the first drives' "connecting, then unreachable after 15 s"; up to three tries, each with a 10 s limit, a growing pause and the service cache cleared on a retry; the MTU request is optional with a 1.5 s limit (an adapter that ignores it must not hold the link); service discovery waits 300 ms; the connection interval is asked to be short once up; writes are at most 20 bytes, and a missing callback on a write-without-response is not a lost link. An `open` that is replaced or closed is answered and cannot leave a retry running (a generation counter).
- **Classic (`BtClassicChannel.kt`):** discovery is stopped before connecting and before pairing; four kinds of socket are tried (secure, insecure, channel 1, insecure channel 1), the one that worked last time first; a round that fails is tried again after a pause; each try has a 10 s watchdog that closes the socket under a hung `connect()`; a close during an open cuts it short; a pairing waits 1.5 s after the bond before it says it is done.
- **`NativeLinkTransport` has its own 75 s limit** on an open, so a radio that never answers cannot leave the session waiting for ever.
- **A connection log, because a link that will not come up says nothing else.** Both channels send `diag` lines (each attempt, the status code, which socket kind worked or failed and the error, the services an adapter lists with their properties, the serial pipe chosen). They go into `LinkDiary` (in memory, 300 lines, shown newest first in Garage → Adapter → Connection log, so a screenshot is enough; the human sends screenshots) and, when recording is on (always in a debug build), into the session recording as `@ link ...` lines. Nothing leaves the phone; the lines hold the adapter's Bluetooth address and nothing about the person or where they are.
- **Not done, on purpose:** a persistent connection log file (it would have to be kept apart from the recordings and pruned); automatic reconnection to the other radio; a foreground service to keep the link up with the screen off (new permission, and the app is a screen-on dashboard).


## The watch, and the exchange file (2026-10-24)

The human ran the app on a Samsung Galaxy Watch4 Classic (Wear OS 3, a 46 mm round 450 x 450 panel) the day before: it connected and drove, and the screens were laid out for a landscape phone and did not fit. *"I need you to really think how this will work on Android watches."* And, with it: a data export and import format, so that data can be pulled and pushed by adb and through the app. The spec is DESIGN.md 16 and `docs/EXCHANGE.md`; this is the reasoning.

**The watch is a form factor of the same app, not a companion.**
- **What the human tested was the whole APK on the watch**, with the watch's own Bluetooth and GPS reaching the adapter. So that is what is built: a watch surface selected at run time (`FormFactor`, DESIGN.md 16.2), over the same services. A Wear OS companion module was the other option and was rejected: Wear's phone-to-watch link is the Google Play Services Data Layer, which CLAUDE.md 1.4 rules out, and two apps would need two release trains. The cost of "one APK" is that a watch carries the phone's code; the APK budget (20 MB an ABI) is unaffected, since the watch's screens are small.
- **Detection:** the platform's own word (`FEATURE_WATCH`, UI mode type watch, `Configuration.isScreenRound`), then, where it cannot say (an emulator, a widget test), a shorter side under 300 lp. No watch the author knows of is above 280 lp and no phone is below 320.
- **Orientation:** CLAUDE.md 3 says landscape only. That is the phone's rule. A watch has an up (12 o'clock), and a landscape lock on a square display would turn the face a quarter. `MainActivity` sets `SCREEN_ORIENTATION_UNSPECIFIED` on a watch before `super.onCreate`. (Wear OS may ignore app orientation requests altogether; either way nothing here draws rotated.) CLAUDE.md 3 is amended.
- **Not on the watch, on purpose:** the HUD, the engine sound, four of the five clusters, Review, Coach, History, Insights, Diagnostics, Pit Stop's numpad, the survey drive. A keypad on a 1.4 inch circle is the opposite of "no text entry" (CLAUDE.md 1.5), and the others have no room to be honest. What the watch records goes to the phone to be looked at (the exchange file), and what it needs arrives the same way.

**A round face is drawn in shares of its diameter, and its corners are empty.**
- Every dimension is a share of D (`TapeWatch`, `WatchFace`), never pixels, so a 192 lp Pixel Watch and a 280 lp stress case use the same rules. Text is placed where the chord of the circle at its height is wide enough (`WatchFace.chordAt`, `roomAt`). A capture and a pixel test (`test/design/watch_round_test.dart`) fail on any lit pixel in the corners.
- **The tape became a ring.** The tach arc (a 240° arc opening at the bottom) already was a watch dial, so the rim *is* the tach (`TachGeometry.rim`: the same painter, the same needle, trail, peak tick and redline, with its ticks inside the band and no numbers); the Money Tape wrapped round the rim is the money ring (72 cells from 12 o'clock, packing to ₹2/5/10... when the trip outgrows it); and the eco bar was bent into the gap at the bottom (`EcoArc`), which costs the face no room.
- **One segment per 200 rpm on the watch**, not per the tier: 35 segments on a 100 lp radius are bolder and cheaper than 70 on it. The fidelity tier starts at Lite and is capped at Balanced.
- **No vignette and no grain on the watch.** A watch is OLED; black costs nothing and the corners must be exactly black. The cost is a flat canvas, and on a 450 px panel a flat black does not band.
- **Numerals are at least weight 500** (`Livery.withNumeralWeightAtLeast`): MONO's Light 300 disappears at an angle on a moving wrist. MONO keeps its character in colour.

**Input: the bezel, a vertical swipe, a tap.**
- The Watch4 Classic has a physical rotating bezel, and any Wear OS watch may have a crown, both delivered as a scroll event from the rotary encoder source, which Flutter's view does not claim. `MainActivity.onGenericMotionEvent` passes it to `DeviceChannel` and an EventChannel (`tapedash/device/rotary`) sends `+1` or `-1` a detent. **Only the direction is sent**: how big a number a detent makes differs by watch, and nothing here can be checked against one.
- **Horizontal swipes are not used in Motion**: on Wear OS a swipe right is the system's own back, so the strip of five pages (which is horizontal) became a vertical reel. **A tap anywhere is the next face** (and round to the first from the last): the easiest gesture for a hand on a wheel, and the harmless one, since a stray tap swaps Drive and Money. This deviates from DESIGN.md 11, which allows only the page swipe, the cluster swipe and the HUD double-tap in Motion: the tap and the bezel *are* the page swipe on a watch, and there is no HUD to double-tap.
- **Back** does nothing while moving (a knock on the wrist must not close the dash) and closes the screen over the reel when parked; **Home** leaves as always.
- **The menu is a wheel**, not a list, and **not a face of the reel**: a wheel inside the reel would take the swipe and the bezel from it and leave no way back to the speed, so the reel's last face is a cover that opens the wheel on a tap. A number (the price) is a dial of the same wheel: the bezel steps ₹0.10 and quick turns ₹1.0.

**Two components were fixed on the way.**
- `MoneyReadout`'s confidence pips were aligned to the top of the numerals' box, not to their baseline, and the box is two pitches tall: at 44 lp they floated 50 lp above the digits. (`Baseline` does not report a baseline to a `Row`.) Fixed with an explicit top padding. It affects the phone too, where the money figures are smaller and it had not shown.
- A parked figure rested part-way through a roll (the known trap in `handoff.md`). `NumeralSettle` (an inherited share) makes every `RollingNumerals` below it glide to the value rounded to the digits it shows as the share rises to 1. The watch's faces use it with the parked share; the phone's screens have not been moved onto it.

**The exchange format (`docs/EXCHANGE.md`).**
- **One text file, newline-delimited JSON, optionally gzip.** Readable with `less` and `jq`, streamable (a year of trips is about 100 MB plain), and extensible without a version bump (unknown lines and fields are ignored). The Dart SDK has gzip and no zip, and the `archive` package was not worth a dependency (CLAUDE.md 5) for what gzip does.
- **Not the SQLite file.** It is private to the app (adb cannot read it on a release build), tied to a schema version, and cannot be merged. Not CSV: it cannot hold a profile or the samples' columns honestly. CSV is a view over the same data (`tool/tdx.dart csv`), which also settles the standing "CSV export" item.
- **A footer with a CRC-32 of everything before it**, checked before anything is applied: a transfer that died, or a full disk, is refused whole with a plain reason, and never half-imported. (The CRC is our own 15 lines; gzip's own checksum covers only the compressed form.)
- **Identity is the start time** (milliseconds), not the database id (which is per device): a trip is the same trip if it started at the same instant. Importing adds and never deletes or overwrites, so two devices end up with both. The same drive recorded on a phone and a watch at once comes in twice, a second apart, and nothing guesses otherwise.
- **The profile is separate from the trips and is applied only when asked**, and a script (adb) must say so. A setup arriving by adb should not silently change the livery, the adapter or the price. **Device-specific settings** (the HUD, the held fidelity tier, the sound) are a different scope and are not in a default export, so pushing a phone's setup to a watch does not copy a windshield flip onto a wrist.
- **Never exported:** trips still open, simulated trips, the adapter's remembered protocol, the connection log, recordings (they are files already) and the running fuel count since the last full tank (it is only right with every trip since, on one device).
- **The folder is the app's own external files directory**, `.../files/exchange/{outbox,inbox,done}`: no permission, and adb reaches it on any Android (it is where the session recordings already go). `result.json` says what the last operation did, so a script can read the outcome.
- **adb triggers the app by an intent extra** (`am start ... --es tapedash.exchange export|import`), because a watch's screen is the worst place to start an export. Imports wait while the car is moving; an export does not.
- **Beam** (phone to watch over our own Bluetooth RFCOMM channel) is designed in EXCHANGE.md 7 and **not built**: it is a native channel nobody can test without both devices on the desk.
- **`adb push` into the app's folder fails on Android 11 and later** ("remote fchown failed"), found on the Wear OS 3 emulator. `tool/adb_exchange.sh push` stages the file in `/data/local/tmp` and copies it with the shell user's `cp`, which works, and the app (in the `ext_data_rw` group) reads it. EXCHANGE.md 5 says so.
- **The watch's connect flow is a `part` of the phone's** (`connect_flow_watch.dart`), not a second flow: the radios, the pairing, the forget-and-pair-again and the trial of the link are the same state machine, and a watch only draws them as wheels and skips the car, the price and the layout (a wrist has no keypad). Two flows would have drifted apart in the one place the real hardware is most likely to need a fix.
- **The watch's menu is one widget for both drives** (`watch_menu.dart`): the adapter drive and the GPS-only drive differ only in which rows it has (a price and a trip to end, or a trip to reset). Back closes its innermost wheel.
- **A wheel opened over a wheel kept the other's row**: the same widget in the same place keeps its state (the trap `handoff.md` already names for lists). Each sheet has its own key; the Data wheel opened on its second row until it did.
- **A watch's first run has no dev button**: the Design Lab's corner button sits where the circle is not.
- **`lib/exchange/` is pure Dart**, in the architecture test's list, so `tool/tdx.dart` runs on a laptop with the same code. The parts that touch the app's settings and the phone (`lib/app/exchange_*.dart`, `lib/platform/exchange_*.dart`) are not.


## Navigation on the HUD, and what "offline" now means (2026-10-24)

The human asked for a simple navigation view on the HUD: if Google Maps is navigating, show the next turn, the ETA and the speed, with Maps doing the routing and the rerouting. This breaks the letter of CLAUDE.md 1 ("strictly offline"), so the contract was amended first, with the wording the human approved: *TapeDash never connects to the internet. It may read the navigation notification of a navigation app the user has installed, which has its own connection; it sends that app nothing.* The plan and to-dos are `docs/NAV.md`.

**Why a notification listener, and not anything else.**
- **Google's Navigation SDK** needs Play Services and an API key (CLAUDE.md 1.4 rules out one, and the app has no account for the other).
- **An accessibility service** (reading Maps' screen) is a far larger permission, breaks with every layout change, and has no business in a car app.
- **Launching Maps with a destination** (`google.navigation:`) would make TapeDash the one that sends Maps something. The human starts navigation in Maps; TapeDash only reads.
- **A notification listener** is a documented Android API, needs no Play Services, works on API 18 and up (so Android 7), uses no network, and reads what Maps already shows the person on the lock screen. Open-source projects do the same (GMapsParser, LGPL-3.0: studied, not copied, as with `obd2`).

**What "enforce the contract" can and cannot mean.** TapeDash cannot stop Google Maps using the internet, and does not need to. What is enforced is TapeDash's own side, in CLAUDE.md 4 and `tool/check_offline.sh`: no network code in the listener; one listener service; the release allowlist is exactly Google Maps; the package is checked before anything else of the notification is read; nothing read is stored or logged. The real cost is not offline-ness but trust: Notification access lets Android show the app every notification. The filter is a promise kept by tests and open source, not by Android, and Garage's explanation says so.

**The map is not a map.** Maps does not give other apps its route, so TapeDash cannot draw the road ahead. What it can draw is Google's arrow, a distance that counts down on our own speed between Maps' updates, and a labelled schematic of the next turn. A real basemap (the optional PMTiles item) would still not show Google's route.

**The spike comes first** because everything depends on a format that is Google's and undocumented. A capture tool, compiled to act only in a debuggable build, writes the structure of Maps' notification to a file for the human to pull. Its output holds street names, so it goes to `recordings/private/`.

**Debug-only things that do not ship:** the debuggable build's allowlist also holds TapeDash's own package, and a stand-in poster in `src/debug/` (with the `POST_NOTIFICATIONS` permission it needs on Android 13+) lets the whole path run on an emulator. `check_offline.sh` reads the main and the merged release manifests only, as it does for `INTERNET` in the debug manifest.

**Reading is opt-in twice, and the app can see that Google Maps is there (2026-10-24).** Notification access is Android's, and it is broad, so TapeDash adds its own gate: the native side opens a notification only while Dart is *listening* (`NavBridge`), and Dart listens only while the Garage switch is on. A phone with access granted and the switch off has TapeDash looking at no notification at all. The manifest gained one `<queries><package android:name="com.google.android.apps.maps"/></queries>` so that Garage can say "Google Maps is not on this phone" instead of silently showing nothing; it asks for no permission and makes no other package visible. The access screen the app opens is Android's; it cannot grant the access itself. Nothing from the navigation feed is stored (an import-graph test holds the storing code to that).

## What running it on emulators decided (2026-10-24)

The navigation feature was built, as the project asks, against a simulator first and run on emulators before any phone: an Android 16 emulator with real Google Maps, and an Android 7.0 emulator (the minimum). What they changed:

- **Only Maps' navigation notification is a turn, and only its removal ends the route.** Maps posts other notifications; a title and a time in one of them would have been shown as a route, and one of them going away would have cleared a live turn. `NavBridge` requires the category `navigation` (seen on the real notification) and follows one notification by its key. A notification that is not in that category is left alone, so a Maps version that dropped the category would show nothing, not something wrong: it fails safe, and the human's capture would show it. The on-device test fails when either check is taken out.
- **What is arriving outranks the warnings.** "Google Maps is not on this phone" and "needs access" are for when nothing arrives; a notification that is heard proves both false. (An emulator image without Maps and a stand-in is what showed it.)
- **Android 7 would have crashed.** `Bitmap.Config.HARDWARE` is Android 8's; naming it is a `NoSuchFieldError` (an `Error`, which a `catch (e: Exception)` does not catch) the first time a navigation notification is read. It is guarded, `NavBridge` leaves out a notification it cannot read instead of failing, and **`tool/check_android_api.sh` (Android lint, NewApi and InlinedApi only) is now in `tool/verify.sh`**, shown to flag exactly that mistake. The lesson kept: the minimum Android is held by a machine check, not by remembering.
- **Android 7 can leave an enabled listener unbound** after its app was killed while bound (the system listed it enabled and never tried to bind it). When the app starts to listen and the listener is not connected, and when it is disconnected, the system is asked to bind it again (`requestRebind`, API 24), and four seconds later the component is switched off and on. It was seen to fire and the listener to come back; **that it was the fallback and not the system's own late rebind is not proved**, and it is kept because it is the documented defence, costs nothing when the listener is connected, and the case it is for is an app update while access is granted.
- **The distance counts down in 10 m steps under about 300 m, and is dropped in the last metres.** Real Maps, not the guess: `500, 450, 400, 350` and then `230, 200, 190, 180, 160, ... 80, 70, 60`, and then no distance, only the instruction. The HUD takes a turn with no distance for the turn itself (the dot fills the junction ring), and a straight `Head toward ...` has no dot.
- **The on-device scripts run on emulators only.** They clear the app's data, which would erase a phone's trips, price and adapter (and `flutter test` uninstalls the app unless told `--no-uninstall`, which they now do). They refuse any device that is not `emulator-*`.
- **A debug build can post the stand-in from inside the app** (`tapedash/nav/standin`) so that an integration test needs no adb and no moving car; a release and a profile build register no such channel (`tool/check_offline.sh` holds `NavBuild`'s release and profile stubs to doing nothing).
- **The test waits for events, not time, when something must not happen.** A fixed wait for "nothing took over" passes on a slow device by being early. After each case a marker notification is posted and waited for; the phone hands notifications to the listener in order, so when the marker has arrived what came before it has been heard.
- **Two things the app cannot fix are written down for the person instead:** Google Maps' own floating window when you switch away from it (Garage says where to turn it off in Android's settings), and the card Maps pops over the screen at a turn (corrected on 2026-10-27, below: Do Not Disturb was the wrong answer).
- **No automatic way to choose the navigation layout.** It takes over while Maps is guiding and gives the chosen layout back; nothing for the person to decide while driving. The review package asks whether that is right.

## The release build with real Maps, and the card (2026-10-27)

The release APK was driven on the Android 16 emulator with real Google Maps, from the cold open to the HUD, with the emulator's position stepped at 30 km/h. The HUD read real turns, distances (450 m, 350 m, 90 m ...), ETAs, a three-line instruction cut at a word with an ellipsis, and the turn with no distance (the dot fills the ring). It also showed what the debug runs had hidden:

- **Maps pops a card over the HUD at turns, and it is not once.** Maps moves its notification into a high-importance channel, "Navigation urgent updates" (`1_2`, importance 4), as a turn comes up; Android 16 shows a card at the top for about 6 s, over the arrow and the distance. Measured on three 170 s drives: 25 of 85 frames with the card (8 cards), then 26 of 85 with Do Not Disturb on (priority only, default policy), then **0 of 85 with "Pop on screen" off for that one channel**, while Maps posted into the channel 28 times. The earlier notes ("the first time", "Do Not Disturb is the answer") were wrong and are corrected in the review package, NAV.md, STATUS.md and the handoff.
- **Garage now says it and opens Android's page for it.** A third note ("If a card drops over the HUD at a turn") and a row that opens Android's notification settings for Google Maps (`Settings.ACTION_APP_NOTIFICATION_SETTINGS` with Maps' package; the app's details page before Android 8). It is the public app-level page, not Maps' channel id: `1_2` is Maps' own and could change, and the page lists whatever the channels are called. It opens a Settings page and sends Maps nothing. Verified on the emulator. Whether Maps does this on the human's Android 15 phone is unknown.
- **Not done: narrowing the listener with Android 14's filter types** (`default_filter_types` / `disabled_filter_types` meta-data, so that the OS delivers only Real-time notifications). It would make the filter partly the OS's own, but if Maps' notification were not classed as Real-time on some phone the HUD would silently show nothing and the person could not re-enable the type. The package filter, its tests and the opt-in already hold the contract. Revisit when the human's capture shows how their phone classes Maps' notification.
- **How the emulator was driven, for the next person:** this image ignores `geo nmea`; `adb emu geo fix <lon> <lat> <alt> <sats> <speed>` takes the speed in **knots** and sets the receiver's speed (`vel=` in `dumpsys location`), which TapeDash's GPS-only drive reads. A pop-up card is found in a raw `screencap` by reading one pixel where the HUD is black; Maps' channel changes are in `adb logcat -b all` as `notification_enqueue ... channel=1_2` and the card as `onHeadsUpPinnedModeChanged`.
